:::{note}

只保留"拍板需要的信息"：结论、依据、分场景判断、代价、成本、周期与适用边界。
完整论证、16 维评分明细、行业对标与 AI 时代前瞻重估，均见完整版。

## 0. 自查：决策者要看的是哪几个维度

给管理层看的选型报告，与给工程团队看的选型报告，组织方式并不一样。前者关心"所以要做什么决定"，
后者关心"凭什么这么判"。按**决策完备性**自查，一份可拍板的选型报告需要覆盖 8 个维度：

| # | 维度 | 决策者的问题 | 本页位置 | 完整版支撑 |
| --- | --- | --- | --- | --- |
| 1 | 结论 | 到底选哪个？一句话说完 | §1.1 | §4.1 |
| 2 | 关键依据 | 凭什么？（≤3 条，不要 16 个维度） | §1.2 | §3.3 §4.1 |
| 3 | 场景适用性 | 我们这种情况算哪一类？ | §2 | §12 |
| 4 | 代价 | 选它要付出什么？有什么坑？ | §3.1 | §4.2 §8.3 |
| 5 | 现金成本 | 要不要掏钱？掏多少？ | §3.2 | §13 |
| 6 | 人力与周期 | 谁来做？多久能上线？ | §3.3 | §5 |
| 7 | 适用边界 | 什么情况下这个结论会失效？ | §4 | §4.4 §6.5 §9.6 |
| 8 | 待办 | 需要谁、在什么时候、拍什么板？ | §5 | §5 |

**自查结论**：第 3 维与第 7 维最容易被漏，也最容易出事。

- 漏掉**场景**，会把两个方向不同的结论混成一个——同一套工具，含与不含公司内部信息时，结论并不一样（见 §2）；
- 漏掉**边界**，评审会就无法回答"这个结论能用到什么时候"。一旦前提变化，决策将失去复核点。

技术团队版的报告（16 维、权重理据、敏感性分析）是支撑第 2 维的证据链，但不适合直接投给决策者。

## 1. 结论与关键依据

### 1.1 结论

| 候选方案 | 技术栈 | 能力分（满分 100） | 判定 |
| --- | --- | --- | --- |
| **Sphinx**（MyST + Mermaid + 静态站） | Python / 构建期渲染 | **84.8** | ✅ **采纳** |
| Docusaurus（MDX + React SSG） | Node.js / 客户端渲染 | 70.6 | 备选（本期不采纳） |

### 1.2 三条关键依据

| # | 依据 | 一句话解释 | 量化口径 |
| --- | --- | --- | --- |
| 1 | **高权重"生死项"落后，且部分无替代** | API 自动生成、PDF 离线交付、跨项目符号引用三项，Docusaurus 只能拿到一半 | 三项权重合计 **21**，Sphinx 21.0 : Docusaurus 10.6（50.5%）；其中 **PDF 交付在 Docusaurus 侧无补齐路径** |
| 2 | **差距跨维度累积，没有单点杠杆** | 不是某一项差，是 10 个维度同时差；调权重也翻不过来 | 极端敌意扰动下 Docusaurus 仍落后 **2.6 分** |
| 3 | **可替代性不对称** | Docusaurus 的领先都在"外观层"，可以换主题追；它的短板补不了 | Docusaurus 领先 3 项（多版本 / 导航 / 上手门槛），全部落在主题与前端形态层 |

> **给管理层的一句话**：Sphinx 赢在**内容生产能力**（能否自动产出 API 参考、PDF、可机器校验的引用），
> Docusaurus 赢在**读者体验与前端形态**（多版本、导航、写作者上手快）。
> 本场景的权重压在内容生产能力一侧——所以结论不取决于"哪个更时髦"。

## 2. 分场景结论：场景 A 与场景 B

**同一套工具，内容边界不同，结论不同。** 这是本页最需要决策者注意的一点。

### 2.1 两个场景的定义

| 对比项 | 场景 A：含公司内部信息 | 场景 B：不含公司内部信息 |
| --- | --- | --- |
| 内容范围 | 含机密 HLD / 接口规范 / 内部设计 | 面向外部开发者的公开文档 |
| 读者 | 内部研发 / 测试 / 运维 + 客户 | 公网开发者 |
| 关键约束 | 必须权限分级、内网可达 | 公网可检索、可托管 |
| 生效的硬性需求 | R1–R10 全部 | R1–R7、R9、R10（**R8 权限分级消失**） |

### 2.2 能力分（满分 100）

| 场景 | Sphinx | Docusaurus | 差距与判定 |
| --- | --- | --- | --- |
| **A 含公司内部信息** | **84.8** | 70.6 | **+14.2**，Sphinx 显著胜出 |
| **B 不含公司内部信息** | **80.6** | 77.0 | **+3.6**，Sphinx 微胜 |

场景 B 的分域明细：

| 域 | 权重 | Sphinx | Docusaurus | 差 |
| --- | --- | --- | --- | --- |
| A · 内容与工程栈适配 | 35 | 33.4 | 23.4 | +10.0 |
| B · Docs-as-Code 契合度 | 22 | 18.4 | 17.0 | +1.4 |
| C · 读者体验与交付 | 28 | 17.0 | **26.2** | **−9.2** |
| D · 组织落地与可持续性 | 15 | 11.8 | 10.4 | +1.4 |
| **合计** | **100** | **80.6** | **77.0** | **+3.6** |

### 2.3 把"要不要花钱"一起算进去

| 场景 | Sphinx（能力 / 成本 / 综合） | Docusaurus（能力 / 成本 / 综合） | 综合胜出 |
| --- | --- | --- | --- |
| A 含公司内部信息 | 84.8 / 88.0 / **86.4** | 70.6 / 76.0 / 73.3 | **Sphinx**（+13.1） |
| B 不含公司内部信息 | 80.6 / 88.0 / 84.3 | 77.0 / 96.0 / **86.5** | **Docusaurus**（+2.2） |

**读法**：

- 场景 A：Sphinx 在**能力与成本两个维度同时领先**，结论稳固，无争议；
- 场景 B：**Docusaurus 才真正反超**——它同时赢在读者体验（C 域 −9.2）与成本（免费检索档 + 一键托管）；
- ⚠️ **"脱敏"本身不足以翻转结论**（差距从 14.2 压到 3.6，Sphinx 仍领先）。要真正翻转，需要场景**整体**改变：
  无大规模 C/C++ API + 无专职文档岗 + 无 PDF 交付（判据见 §4.2）。

> **本项目同时承载两类内容**，正确做法不是二选一，而是**「一份源、两个发布目标」**：
> 内部面走 Sphinx（能力与成本双优），对外面若确需更强前端体验，可在同一份 Markdown 源上加一条渲染链。
> **混用工具链可接受，混用内容源不可接受。**

## 3. 代价、成本与周期

### 3.1 选择 Sphinx 的代价（真实存在，逐条给缓解）

| 已知代价 | 影响 | 缓解措施 | 验收口径 |
| --- | --- | --- | --- |
| 标记语法学习曲线陡 | 研发写作者上手慢 | 全站改用 MyST（Markdown）+ 模板仓库 | 新人首篇文档 PR 合入 ≤ 2 天 |
| 多版本管理依赖第三方插件 | 版本切换体验弱于 Docusaurus | 引入成熟版本插件 + 主题版本菜单 | 同时在线 ≥ 3 个版本 |
| 默认主题观感朴素 | 对外门户形象偏弱 | 换现代主题（pydata / Furo）+ 品牌 CSS | 首屏 LCP < 2.5s |
| 中文检索分词弱 | 国内读者命中率下降 | jieba 分词补丁，或部署独立搜索服务 | 抽样 50 条查询，Top-5 命中率 ≥ 80% |
| 无交互 demo 能力 | 对外文档缺在线 playground | 关键示例页内嵌轻量交互组件（按需） | 至少 1 个 API 示例可在线运行 |

### 3.2 现金成本（要不要掏钱）

**两个工具的本体都不收费**（Sphinx 为 BSD、Docusaurus 为 MIT），差别不在"买不买"，
而在**生态付费墙与内网可达性**。下面两张表分别从**工具横比**与**场景纵比**两个角度看。

**表一：两个工具的成本结构横比**

| 成本项 | Sphinx 栈 | Docusaurus 栈 | 谁更省 |
| --- | --- | --- | --- |
| 工具本体 | BSD-2-Clause，免费可商用 | MIT，免费可商用 | 打平（均 ¥0） |
| API 参考生成 | Breathe（BSD）+ Doxygen（免费），一级支持 | 无第一方方案，需第三方桥接链（多 MIT）且自维护 | **Sphinx** |
| 主题 | 免费主题可选（alabaster / Furo / pydata） | 官方主题免费，开箱观感更好 | 打平 |
| 多版本 | 依赖第三方插件（免费，但靠社区 fork 续命） | 内置，免费 | **Docusaurus** |
| 检索 | 内置离线搜索免费（中文需 jieba 补丁） | Algolia DocSearch 免费档——**仅限公网可访问站点** | 场景相关（见表二） |
| 托管 | GitHub Pages / 自建 / Read the Docs | GitHub Pages / Vercel / Netlify / 自建 | 打平 |
| 内网与离线构建 | 可完全离线，依赖少、内存占用数百 MB 级 | npm 依赖需内网镜像；构建吃内存（>12k 页 OOM，需 16–32GB） | **Sphinx** |

> **E 域（许可与总拥有成本，满分 100，分值越高越省）**：**Sphinx 88.0，在场景 A / B 恒定**；
> **Docusaurus 76.0（场景 A）→ 96.0（场景 B）**。这个落差全部来自两处——
> "内网用不了免费检索档"与"npm 依赖需内网镜像"。

**表二：两个场景下的实际现金支出**

| 成本项 | 场景 A（含内部信息） | 场景 B（不含内部信息） | Sphinx / Docusaurus 的差异点 |
| --- | --- | --- | --- |
| 工具本体 | ¥0 | ¥0 | 两者均免费，无差异 |
| 检索 | 自建离线搜索（人力）或 Algolia 付费账户 | Algolia DocSearch 免费档 | Sphinx 自带离线搜索；**Docusaurus 在内网用不了免费档**，必须自建或付费 |
| 托管 | 自建内网服务器（多为既有资源），或 Read the Docs Business **$50/月起** | GitHub Pages 免费 | 打平；但 Docusaurus 侧内网还需 npm 私服 |
| 权限控制 | 必需 → 自建 SSO 或托管付费档 | 不需要 | Sphinx 多页静态更易接内网 SSO 网关；Docusaurus 依赖平台级密码保护，链路更长 |
| 大内存构建机 | 视站点规模 | 免费档通常足够 | Sphinx 数百 MB；Docusaurus 在数万页量级需 16–32GB，成本更高 |
| **年化现金支出** | **≈ $0（自建）/ $600–3,000（用付费托管）** | **≈ ¥0** | 见上 |

**一句话结论**：**不是工具决定要不要花钱，是内容边界决定。**

- 文档只要公开 → 两个工具都能做到**零现金成本**（场景 B 下 Docusaurus 的 E 域甚至反超到 96.0）；
- 一旦含内部信息 → **必然产生权限/托管支出或自建成本**——权限分级在托管平台上是付费功能，
  这也正是 C3（权限与分级）高权重的现金解释（见 §2.2 场景 B 分域表）；
- 两个工具之间的成本差只集中在两处：**内网检索**（Docusaurus 无法使用免费档）与**构建内存**（Docusaurus 侧更吃资源）。

### 3.3 人力与周期（启动后 6 周）

| 周 | 动作 | 交付物 | 验收口径 |
| --- | --- | --- | --- |
| W1 | 冻结选型与构建基线 | 评审结论 + 依赖清单 + CI 骨架 | 三方评审通过；构建零告警 |
| W2 | 写作模板与目录规范 | 6 类文档模板 + 目录 lint | lint 全绿；示例页可复制即用 |
| W3 | API 自动生成 PoC | 跑通 1 个模块的自动生成链 | 覆盖该模块 100% 公开符号 |
| W4 | 多版本构建 PoC | 同时构建 2 个版本 | 版本切换器可用 |
| W5 | 双版本对比评审 + CI 门禁 | PR 自动产出修改前后对照页 | 对照页可评审 |
| W6 | 权限分级与双发布 | 内网站（SSO）+ 对外站 + PDF | 三级权限用例通过 |

**前置依赖（需管理层协调）**：W3 依赖研发侧补充头文件注释规范，须在 W1 同步启动沟通，
否则 W3 会因注释覆盖率不足而阻塞。

## 4. 适用边界：什么时候要回头重审

### 4.1 三条前提

| # | 前提 | 若不成立 |
| --- | --- | --- |
| 1 | 存在"一份源、三类交付面"的需求（内部站 / 对外门户 / 离线 PDF） | 若只做对外站，结论向 Docusaurus 移动 |
| 2 | 存在大规模 C/C++ 头文件，API 参考需自动生成 | 若 API 以 REST / TS 为主，该项权重下降，差距收窄 |
| 3 | 有一个承担文档体系职责的岗位或明确编制 | 若无专职岗、由前端团队兼管，Sphinx 的组织成本上升 |

### 4.2 改判条件（满足 ≥3 条 → 重估）

| # | 条件 |
| --- | --- |
| 1 | 文档只对外、无机密分级需求 |
| 2 | 不需要 PDF / 离线交付件 |
| 3 | API 以 REST / GraphQL / TS / Python 为主，无大规模 C/C++ 头文件 |
| 4 | 需要交互式 demo / playground，或要与官网、博客同站 |
| 5 | 维护者是无专职技术写作岗的前端 / 全栈团队 |
| 6 | 需要开箱即用的多版本文档托管，不愿引入第三方插件 |

> 注：「修改前后双版本对比评审」不在改判条件内——两个候选均无内置功能，实际靠 Git 源 diff 承载，不构成选型差异。

### 4.3 两点稳健性压力测试

| 压力 | 结果 |
| --- | --- |
| 权重敏感性 | 权重在理据可支撑区间内扰动（含极端敌意扰动），结论**不翻转**（最差仍领先 2.6 分） |
| 时间尺度（5–10 年 AI 时代） | 同一模型重算为 **Sphinx 88.4 : Docusaurus 66.6**，差距由 14.2 **扩大到 21.8**，**结论强化** |

## 5. 下一步：需要拍板的三件事

| # | 待决策项 | 建议 | 需要的角色 |

| 1 | 是否采纳 Sphinx 作为统一文档平台 | 采纳（场景 A 能力与成本双优） | 项目负责人 / 技术负责人 |
