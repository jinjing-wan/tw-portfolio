## 1. 结论与关键依据

### 1.1 结论

| 候选方案 | 技术栈 | 能力分（满分 100） | 判定 |
| --- | --- | --- | --- |
| **Sphinx**（MyST + Mermaid + 静态站） | Python / 构建期渲染 | **86.4** | ✅ **采纳** |
| Docusaurus（MDX + React SSG） | Node.js / 客户端渲染 | 70.2 | 备选（本期不采纳） |

### 1.2 三条关键依据

| # | 依据 | 一句话解释 | 量化口径 |
| --- | --- | --- | --- |
| 1 | **高权重"生死项"落后，且部分无替代** | API 自动生成、PDF 离线交付、跨项目符号引用三项，Docusaurus 只能拿到一半 | 三项权重合计 **23**，Sphinx 23.0 : Docusaurus 11.8（51.3%）；其中 **PDF 交付在 Docusaurus 侧无补齐路径** |
| 2 | **差距跨维度累积，没有单点杠杆** | 不是某一项差，是多个维度同时差；调权重也翻不过来 | 极端敌意扰动下 Docusaurus 仍落后 **5.2 分** |
| 3 | **可替代性不对称** | Docusaurus 的领先都在"外观层"，可以换主题追；它的短板补不了 | Docusaurus 领先 2 项（多版本 / 导航），全部落在主题与前端形态层；**写作者门槛在"有专职岗"前提下已打平** |

> **给管理层的一句话**：Sphinx 赢在**内容生产能力**（能否自动产出 API 参考、PDF、可机器校验的引用），
> Docusaurus 赢在**读者体验与前端形态**（多版本、导航、写作者上手快）。
> 本场景的权重压在内容生产能力一侧——所以结论不取决于"哪个更时髦"。
> 本版的前提是**已配备专职文档岗**（见 §1.3），该前提使差距由 14.2 扩大到 16.2。

### 1.3 本报告的组织前提：配备专职文档岗

本报告的评分建立在一条**明确的组织前提**上：**已配备专职文档岗**（技术文档工程师，1 人起）——
文档体系由该岗主写与治理，研发工程师按规范补充头文件注释与初稿。

这条前提直接改变总分的**两个来源**（一降一升、净权重不变）：

| 维度 | 无专职岗 | **有专职岗（本版前提）** | 影响 |
| --- | --- | --- | --- |
| 写作者门槛（D1） | 权重 6，Sphinx 3 / D 4（D 领先） | 权重 **4**，Sphinx **4** / D 4（**打平**） | Sphinx 的组织短板被补齐 |
| 交叉引用与术语治理（A5） | 权重 4 | 权重 **6** | 专职岗的核心职责被放大，Sphinx 领先扩大 |

**净效果**：Sphinx 从 **84.8** 升至 **86.4**，Docusaurus 从 70.6 微降至 **70.2**，差距由 **14.2 扩大到 16.2**。

一句话：**有专职文档岗，是"放大 Sphinx 优势"的条件**；反之，无专职岗会收窄差距——
§6.3 的「对外产品文档站」场景正是无专职岗，结论在那里反转为 Docusaurus 领先。

> ⚠️ 这条前提本身是一项**持续人力成本**（1 名 TW 的年薪）与**单点风险**（该岗离职会带走规范与工具链知识），
> 它不进上面的现金账单，但是长期成本曲线的真实分水岭（见 §3.2 与完整版 §8.3）。

## 2. 分场景结论：场景 A 与场景 B

**同一套工具，内容边界不同，结论不同。** 这是本页最需要决策者注意的一点。

### 2.1 两个场景的定义

| 对比项 | 场景 A：含公司内部信息 | 场景 B：不含公司内部信息 |
| --- | --- | --- |
| 内容范围 | 含机密 HLD / 接口规范 / 内部设计 | 面向外部开发者的公开文档 |
| 读者 | 内部研发 / 测试 / 运维 + 客户 | 公网开发者 |
| 关键约束 | 必须权限分级、内网可达 | 公网可检索、可托管 |
| 生效的硬性需求 | R1–R11 全部 | R1–R7、R9、R10、R11（**R8 权限分级消失**） |

### 2.2 能力分（满分 100）

| 场景 | Sphinx | Docusaurus | 差距与判定 |
| --- | --- | --- | --- |
| **A 含公司内部信息** | **86.4** | 70.2 | **+16.2**，Sphinx 显著胜出 |
| **B 不含公司内部信息** | **82.2** | 76.6 | **+5.6**，Sphinx 微胜 |

场景 B 的分域明细：

| 域 | 权重 | Sphinx | Docusaurus | 差 |
| --- | --- | --- | --- | --- |
| A · 内容与工程栈适配 | 37 | 35.4 | 24.6 | +10.8 |
| B · Docs-as-Code 契合度 | 22 | 18.4 | 17.0 | +1.4 |
| C · 读者体验与交付 | 28 | 17.0 | **26.2** | **−9.2** |
| D · 组织落地与可持续性 | 13 | 11.4 | 8.8 | +2.6 |
| **合计** | **100** | **82.2** | **76.6** | **+5.6** |

### 2.3 把"要不要花钱"一起算进去

| 场景 | Sphinx（能力 / 成本 / 综合） | Docusaurus（能力 / 成本 / 综合） | 综合胜出 |
| --- | --- | --- | --- |
| A 含公司内部信息 | 86.4 / 88.0 / **87.2** | 70.2 / 76.0 / 73.1 | **Sphinx**（+14.1） |
| B 不含公司内部信息 | 82.2 / 88.0 / 85.1 | 76.6 / 96.0 / **86.3** | **Docusaurus**（+1.2） |

**读法**：

- 场景 A：Sphinx 在**能力与成本两个维度同时领先**，结论稳固，无争议；
- 场景 B：**Docusaurus 才真正反超**——它同时赢在读者体验（C 域 −9.2）与成本（免费检索档 + 一键托管）；
- ⚠️ **"脱敏"本身不足以翻转结论**（差距从 16.2 压到 5.6，Sphinx 仍领先）。要真正翻转，需要场景**整体**改变：
  无大规模 C/C++ API + 无专职文档岗 + 无 PDF 交付（判据见 §4.2）。

> **本项目同时承载两类内容**，正确做法不是二选一，而是**「一份源、两个发布目标」**：
> 内部面走 Sphinx（能力与成本双优），对外面若确需更强前端体验，可在同一份 Markdown 源上加一条渲染链。
> **混用工具链可接受，混用内容源不可接受。**

## 3. 代价、成本、周期与落地路径

### 3.1 选择 Sphinx 的代价（真实存在，逐条给缓解）

| 已知代价 | 影响 | 缓解措施 | 验收口径 |
| --- | --- | --- | --- |
| 标记语法学习曲线陡 | 研发写作者上手慢 | 全站改用 MyST（Markdown）+ 模板仓库 + **专职岗承担指令体系** | 新人首篇文档 PR 合入 ≤ 2 天 |
| 多版本管理依赖第三方插件 | 版本切换体验弱于 Docusaurus | 引入成熟版本插件 + 主题版本菜单 | 同时在线 ≥ 3 个版本 |
| 默认主题观感朴素 | 对外门户形象偏弱 | 换现代主题（pydata / Furo）+ 品牌 CSS | 首屏 LCP < 2.5s |
| 中文检索分词弱 | 国内读者命中率下降 | jieba 分词补丁，或部署独立搜索服务 | 抽样 50 条查询，Top-5 命中率 ≥ 80% |
| 无交互 demo 能力 | 对外文档缺在线 playground | 关键示例页内嵌轻量交互组件（按需） | 至少 1 个 API 示例可在线运行 |

### 3.2 现金成本（要不要掏钱）

**两个工具的本体都不收费**（Sphinx 为 BSD、Docusaurus 为 MIT），差别不在"买不买"，
而在**生态付费墙与内网可达性**。下面两张表分别从**工具横比**与**场景纵比**两个角度看。

**表一：两个工具的成本结构横比**

| 成本项 | Sphinx 栈 | Docusaurus 栈 | 谁更省 |
| --- | --- | --- | --- |
| 工具本体 | BSD-2-Clause，免费可商用 | MIT，免费可商用 | 打平（均 ¥0） |
| API 参考生成 | Breathe（BSD）+ Doxygen（免费），一级支持 | 无第一方方案，需第三方桥接链（多 MIT）且自维护 | **Sphinx** |
| 主题 | 免费主题可选（alabaster / Furo / pydata） | 官方主题免费，开箱观感更好 | 打平 |
| 多版本 | 依赖第三方插件（免费，但靠社区 fork 续命） | 内置，免费 | **Docusaurus** |
| 检索 | 内置离线搜索免费（中文需 jieba 补丁） | Algolia DocSearch 免费档——**仅限公网可访问站点** | 场景相关（见表二） |
| 托管 | GitHub Pages / 自建 / Read the Docs | GitHub Pages / Vercel / Netlify / 自建 | 打平 |
| 内网与离线构建 | 可完全离线，依赖少、内存占用数百 MB 级 | npm 依赖需内网镜像；构建吃内存（>12k 页 OOM，需 16–32GB） | **Sphinx** |

> **E 域（许可与总拥有成本，满分 100，分值越高越省）**：**Sphinx 88.0，在场景 A / B 恒定**；
> **Docusaurus 76.0（场景 A）→ 96.0（场景 B）**。这个落差全部来自两处——
> "内网用不了免费检索档"与"npm 依赖需内网镜像"。

**表二：两个场景下的实际现金支出**

| 成本项 | 场景 A（含内部信息） | 场景 B（不含内部信息） | Sphinx / Docusaurus 的差异点 |
| --- | --- | --- | --- |
| 工具本体 | ¥0 | ¥0 | 两者均免费，无差异 |
| 检索 | 自建离线搜索（人力）或 Algolia 付费账户 | Algolia DocSearch 免费档 | Sphinx 自带离线搜索；**Docusaurus 在内网用不了免费档**，必须自建或付费 |
| 托管 | 自建内网服务器（多为既有资源），或 Read the Docs Business **$50/月起** | GitHub Pages 免费 | 打平；但 Docusaurus 侧内网还需 npm 私服 |
| 权限控制 | 必需 → 自建 SSO 或托管付费档 | 不需要 | Sphinx 多页静态更易接内网 SSO 网关；Docusaurus 依赖平台级密码保护，链路更长 |
| 大内存构建机 | 视站点规模 | 免费档通常足够 | Sphinx 数百 MB；Docusaurus 在数万页量级需 16–32GB，成本更高 |
| **年化现金支出** | **≈ $0（自建）/ $600–3,000（用付费托管）** | **≈ ¥0** | 见上 |

**一句话结论**：**不是工具决定要不要花钱，是内容边界决定。**

- 文档只要公开 → 两个工具都能做到**零现金成本**（场景 B 下 Docusaurus 的 E 域甚至反超到 96.0）；
- 一旦含内部信息 → **必然产生权限/托管支出或自建成本**——权限分级在托管平台上是付费功能，
  这也正是 C3（权限与分级）高权重的现金解释（见 §2.2 场景 B 分域表）；
- 两个工具之间的成本差只集中在两处：**内网检索**（Docusaurus 无法使用免费档）与**构建内存**（Docusaurus 侧更吃资源）。
- ⚠️ 别漏掉**人力成本**：本版的"有专职文档岗"前提本身即一项持续支出（1 名 TW 的年薪），它不在上面的现金账单里，却是长期成本曲线的真实分水岭（见 §1.3）。

| 周 | 动作 | 交付物 | 验收口径 |

否则 W3 会因注释覆盖率不足而阻塞。

### 3.4 参照对象：三家同业形态，我们照谁来搭

选型结论再对，落到实施时团队还是会问：**业界同行到底怎么做的？我们照谁？**
三家 GPU 厂商的文档栈已**一手实测**（读原始 HTML / 响应头 / 静态资源，非二手转述），
结论是——**它们不是"三代技术"，而是三种形态**：共用同一个符号提取后端（Doxygen 系），
分野全在**前端与组织**。

| 维度 | NVIDIA CUDA | 摩尔线程 MUSA | 沐曦 MetaX |
| --- | --- | --- | --- |
| 渲染内核 | Sphinx + Breathe | Docusaurus v3.10.1 + 自研 MDX 生成器 | **Sphinx**（源为 reST） |
| API 符号提取 | Doxygen → Breathe | Doxygen 只取 XML + 自研转换 | Doxygen 系 |
| 主题 | 自研主题（pydata 基座，专有许可） | Docusaurus 原生 | sphinx_rtd_theme + 自写 CSS |
| 门户 | 与文档同栈 | Next.js（与文档分栈） | Next.js（文档内核嵌在自研网关内） |
| 多版本 | 按 release 归档 | 4 版本并存（内置） | 版本路径段 |
| PDF / 离线交付 | 有 | **无**（实测 0 个 `.pdf` 链接） | 有（下载件） |
| 权限分级 | 有 | 无（全公开） | 未证实 |
| 符号清单 `objects.inv` | intersphinx | 无 | **生产在用** |
| 起步时间锚点 | 2007 起，20 年演进 | MUSA 2022 起，约 4 年 | **2021-12 起**（`sphinx-quickstart`） |
| 组织归属 | 专职 TW 团队 | 前端 / 研发兼任 | 推测有文档团队 |

**三条判断**：

1. **摩尔线程走的是"最省组织成本"的路**（Docusaurus + 自研管线、前端兼任）——代价是自建一条 API 桥接链，
   且**无 PDF、无分级**。它的场景是纯公开门户，与本场景（需分级 / 需 PDF / 内网交付）不同。
2. **沐曦走的是"最贴近本场景"的路**：**Sphinx 内核 + 自建门户**——既保住 Sphinx 的符号图与多格式能力
   （`objects.inv` 在生产环境真实可用），又用一层自研门户解决观感，同时绕开了托管平台在权限与分级上的付费限制。
3. **NVIDIA 是天花板，不是起点**——20 年积累 + 专职团队，不适合作为"从 0 起步"的参照。

> **一句话结论**：**本方案参照沐曦形态（Sphinx 内核 + 最小门户），按简化版起步**——
> 先在 Sphinx 内核上跑通"能构建、能自动产 API、能发布"，门户层后补，不必在起步阶段动前端。

### 3.5 搭建路径：四步法

参照沐曦的栈，把"从 0 到基础可用"拆成四步。**每步给出"要干什么 / 验收要求 / 交付物"**，
便于项目管理者排期、岗位管理者定职责。

| 步 | 要干什么 | 验收要求 | 交付物 |
| --- | --- | --- | --- |
| ① 打地基 | 初始化 Sphinx 项目；设计目录树与导航；选主题 + 品牌 CSS；定文档类型模板（教程 / 指南 / 参考 / 概念）；定写作规范与术语表；建 Git 仓库与目录 lint | 构建零告警；模板复制即用；lint 全绿 | 可构建的文档仓库 · 配置与目录树 · 模板库（2–3 类）· 写作规范与 lint 脚本 |
| ② 通链路 | 配 Doxygen；用 Breathe 把头文件桥入 Sphinx；跑通 1 个核心库；与研发对齐注释规范 | 覆盖该模块 **100% 公开符号**；生成页非空壳；改头文件即自动更新 | 可复现的 API 生成链 · 1 个模块的 API 参考页 · 研发注释规范 |
| ③ 建流水线 | CI：提交触发构建 + 告警门禁；CD：产物自动发布到静态位（内网 = Jenkins + 依赖镜像） | 提交即自动构建；有告警自动拦截；发布自动或一条命令 | CI/CD 配置 · 发布脚本 · 一个可访问的站点 |
| ④ 产内容 + 交接 | 产出首批真实内容（入门 / 安装 / 1 个核心库 API）；写《体系维护手册》与《新人上手指南》 | 内容符合模板与术语规范；他人可照规范独立写作 | 首批 15–25 页内容 · 维护手册 · 上手指南 |

> **关键提示**：四步中 **② 是唯一的技术难点**，也是本场景与"普通文档站"的根本区别——
> **GPU 厂商的 API 参考页不能手写，必须有自动抽取链。**

### 3.6 第一阶段工期（四档口径）

| 档位 | 范围 | 人日（1 名专职文档岗） | 日历 |
| --- | --- | --- | --- |
| **L1 骨架可用** | ① 打地基 + ③ 建流水线 | 8 | **1.5–2 周** |
| **L2 基础可用（推荐起步）** | L1 + ② 通链路 + ④ 前段（首批内容 + 检索） | **27** | **5–6 周** |
| **L3 完整启动计划** | L2 + 多版本 + 权限分级 + PDF 双发布 | 40–45 | 8–10 周 |
| **L4 对标同业规模** | 全 API 面 + 多芯片系列 + 全量内容 | — | **6–12 个月** |

**两点说明**：

- **同业长成全 API 面约需 4 年**（沐曦 2021-12 起、摩尔线程 2022 起），但那是含量产产品迭代的**公司级**时间；
  **L2 的 5–6 周才是"能开始产出价值"的时点**。
- L4 的 6–12 个月**瓶颈在内容量，不在工具**——工具在 L2 就全部就位。

### 3.7 角色与输入依赖：文档岗干活，三条命脉在别人手里

L1 / L2 的执行都是专职文档岗（1 人起，承担全部 27 人日），**但两个阶段对别人的依赖性质不同**：
**L1 要的是一次性输入，L2 要的是持续投入**。下表按阶段分列，是项目管理需要协调的全部内容。

| 角色 / 输入方 | L1 要提供什么 | L2 要提供什么（新增 / 升级） | 关键度 |
| --- | --- | --- | --- |
| **技术文档工程师** | 搭骨架、建 Git 仓、写 CI/CD、出模板（**8 人日**） | 配 API 抽取链、写首批内容、接检索、拉通评审（**追加 19 人日**） | 主执行 |
| **研发负责人 / 架构师** | 拍板文档仓结构（独立仓 vs 与代码仓同仓）、技术栈、头文件位置 | **批准注释补全排期**、指定各模块 API 侧接口人 | 高 · 第 1 周 |
| **研发工程师（API 作者）** | 1 个核心库的头文件 + 注释覆盖率基线 | **把该库头文件注释补到可生成**，此后增量维护 | **最高 · 最大变量** |
| **领域专家 / SME** | 评审 2–3 类模板 | **逐页评审首批内容的正确性**（入门 / 安装 / API 说明） | 中 · L2 新增 |
| **DevOps / 运维** | 构建机、Python 依赖内网镜像、CI runner、静态发布位 | 装 Doxygen、CI 扩展为「抽取 + 构建 + lint」、构建机扩容 | 高 · 周期最长 |
| **Release / 产品经理** | — | 版本号、API 冻结窗口、文档与版本的对应关系 | 中 · L2 新增 |
| **项目管理 / 岗位负责人** | 批 L1 计划、协调上述三条依赖 | 批 19 人日预算、协调注释排期与 SME 评审 | 全程 |
| 安全 / 合规 · 设计 | 轻量告知内网口径 | 内网发布口径、品牌 CSS（按需） | 低 |

**L1 与 L2 的本质差别**：L1 的三条依赖是**一次性输入**——一个决策、一份样本、一套环境，给完即可开工；
L2 变成**持续性投入**——研发要排数天注释工时、SME 要审十几页内容、运维要动构建机，
**这些都不占 TW 的 27 人日，属于额外人力**。

> **因此 L2 的真实风险不是"TW 干不完"，而是"研发的注释排期批不下来"。**
> 只要注释覆盖率上不去，② 的 API 参考页就是空壳，内容写得再多也撑不起参考手册。

> **一句话结论**：**文档岗出 8 人日骨架 + 27 人日 MVP；研发负责人出 1 个决策、研发工程师出 1 份样本
> （L2 起升级为整库注释补全）、运维出 1 套环境（L2 起扩展为含 Doxygen 的构建链）；L2 另需 SME 内容评审
> 与版本窗口两项新输入。** 三条输入若不在第一周到位，第一阶段会从 2 周拖到 3–4 周——
> **拖的是等输入的时间，不是干活的时间。**

## 4. 适用边界：什么时候要回头重审

### 4.1 三条前提

| # | 前提 | 若不成立 |
| --- | --- | --- |
| 1 | 存在"一份源、三类交付面"的需求（内部站 / 对外门户 / 离线 PDF） | 若只做对外站，结论向 Docusaurus 移动 |
| 2 | 存在大规模 C/C++ 头文件，API 参考需自动生成 | 若 API 以 REST / TS 为主，该项权重下降，差距收窄 |
| 3 | **已有专职文档岗**（本版即以此前提评分，见 §1.3） | 若撤岗、改由前端 / 研发团队兼管，Sphinx 的组织成本上升，差距由 16.2 收窄 |

### 4.2 改判条件（满足 ≥3 条 → 重估）

| # | 条件 |
| --- | --- |
| 1 | 文档只对外、无机密分级需求 |
| 2 | 不需要 PDF / 离线交付件 |
| 3 | API 以 REST / GraphQL / TS / Python 为主，无大规模 C/C++ 头文件 |
| 4 | 需要交互式 demo / playground，或要与官网、博客同站 |
| 5 | 维护者是无专职技术写作岗的前端 / 全栈团队 |
| 6 | 需要开箱即用的多版本文档托管，不愿引入第三方插件 |

> 注：「修改前后双版本对比评审」不在改判条件内——两个候选均无内置功能，实际靠 Git 源 diff 承载，不构成选型差异。

### 4.3 两点稳健性压力测试

| 压力 | 结果 |
| --- | --- |
| 权重敏感性 | 权重在理据可支撑区间内扰动（含极端敌意扰动），结论**不翻转**（最差仍领先 5.2 分） |
| 时间尺度（5–10 年 AI 时代） | 同一模型重算为 **Sphinx 89.2 : Docusaurus 66.2**，差距由 16.2 **扩大到 23.0**，**结论强化** |

## 附录 C：术语与工具速查

| 术语 | 一句话解释 |
| --- | --- |
| Sphinx | Python 生态的文档生成器：把文本源构建成 HTML / PDF 站点 |
| reST / MyST | Sphinx 的两种写作语法：reST 是原生语法，MyST 是 Markdown 版 |
| 目录树（toctree） | 定义文档目录与导航顺序的指令——**信息架构的载体** |
| Doxygen | 从头文件抽取 C/C++ 符号（函数 / 参数 / 返回值）的工具 |
| Breathe | 把 Doxygen 的产出桥接进 Sphinx 的插件 |
| `objects.inv` | Sphinx 的"跨项目符号清单"，支撑跨文档的符号级引用 |
| Docs-as-Code | 把文档当代码管理：进版本库、走评审、自动构建、自动发布 |
| CI / CD | 持续集成 / 持续交付：提交即自动构建、校验、上线 |
| lint | 自动检查格式与规范的脚本，不合格即报错 |
| 告警门禁（-W） | 构建时把"告警"升级为"错误"，**有任何告警就不许合入** |
