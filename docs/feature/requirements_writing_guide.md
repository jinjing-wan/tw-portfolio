# 需求文档书写规范与提示词（company_doc_init 适用）

> 本文档沉淀「公司文档初始化项目」规格中 **第二章（高层级需求）** 与 **第三章（高层级需求拆分）** 的书写规范，
> 可作为可复用提示词，直接喂给 AI 生成/重写对应章节。示例均取自 `company_doc_init_spec.rst`。

---

## 1. 目的
统一需求文档写法：高层级需求（HL）→ 底层级需求（LL）的拆解，以及每个 LL 的「模块职责」描述，
保证文档可读、可评审、可追踪、**可验收**。

## 2. 概念层级
- **高层级需求 HL（Epic）**：项目级目标，本例 4 条（HL-01~04）。
- **Feature / Sub-feature**：交付物/能力桶。文档类型特性 Feature-A~F；流水线子特性 HL-03-A~F。
- **底层级需求 LL**：可落地、可验收的粒度。每条 LL 对应一个 HL，并引用相关 Feature / Sub-feature 编号。

## 3. 通用属性（HL 与 LL 均必须包含）
下列 6 项属性 **必须包含**，且 **统一用「两列表格（list-table，header-rows: 0）」呈现**，不得使用逐行加粗内联写法。

| 属性 | 说明 | 取值示例 |
| --- | --- | --- |
| Requirement ID | 唯一编号（HL-01 / LL-001） | HL-01 / LL-001 |
| Priority | 优先级 | P0 / P1 / P2 |
| Target Release | 目标版本/季度 | R1 / R2 / R3 |
| Change History | 版本与日期 | v1.0 初稿 2026-10-12 |
| 对应 Feature / Sub-feature | 引用的 feature 或 sub-feature 编号 | Feature-A / HL-03-A |
| 是否可测试（Testable） | 该需求是否可被验证/验收；不可测试需说明原因或替代验证方式 | 可测试 / 部分可测试 / 不可测试 |

**两列表格格式（强制）**：

```rst
.. list-table:: <Requirement ID> 属性
   :header-rows: 0
   :widths: 32 68

   * - Requirement ID
     - HL-01
   * - Priority
     - P0
   * - Target Release
     - R1（2026-Q4）
   * - Change History
     - v1.0 初稿（2026-10-12）
   * - 对应 Feature/Sub-feature
     - Feature-A / B / C / D / E / F
   * - 是否可测试
     - 可测试
```

> 表格必须放在需求标题（HL-x 或 3.2.x 小节标题）之后、目标描述/场景描述之前；
> 表格前后各保留一个空行。`<Requirement ID>` 替换为该需求真实编号（如 `HL-01 属性` / `LL-001 属性`）。

> **是否可测试（Testable）取值约定**
> - **可测试**：存在明确验收条件，可通过检查/演示/用例验证（如"平台可用且检索成功"）。
> - **部分可测试**：核心交付物可验证，但部分效果只能定性（如 onboarding 的 ramp-up 周期靠问卷反馈）。
> - **不可测试**：纯目标性/原则性陈述（如"提升团队幸福感"），需在备注写替代度量方式或删除该需求。

## 4. 第二章写法（高层级需求）
- 只列 HL 需求，**不下钻**子特性/底层级需求（下钻放到第三章）。
- 每条 HL 结构：先「6 项属性（两列表格）」，再一段**目标描述**（做什么 + 范围）。
- 属性**必须**用两列表格（`list-table` + `:header-rows: 0`）呈现，禁止逐行加粗内联写法（见 §3）。

## 5. 第三章写法（高层级需求拆分）

### 5.1 3.1 映射表
- 用 `list-table`，列：**需求编号 | 高层级需求 | 底层级需求(LL) | 大致内容**。
- 一行 HL 可对应多行 LL（LL 编号空格分隔）。

### 5.2 3.2 底层级需求详述
每个 LL 一节（`3.2.x`），固定三段：
1. **属性块**（6 项通用属性，两列表格形式，见 §3）
2. **场景描述**（1~2 段：为什么要做、解决什么问题）
3. **模块职责表**（见 5.3）

### 5.3 模块职责表格式
- 列：**模块 | 需要做什么 | 前提条件 | 触发条件 | 执行结果**
- 标准 9 模块（**须逐模块填写**；无关模块填 `否（无职责） / — / — / —`）：
  研发部 / 测试质量部 / 产品部 / 运维SRE / 市场售前 / 客户支持 / 管理层PMO / HR新人培训 / 技术写作组(Owner)
- 原则：明确 **「在什么条件下，触发了什么，产生了什么结果」**。
- 标注「（主）」表示该模块是此项职责的主责方。

## 6. 复用提示词（直接喂给 AI）
```
你是技术写作工程师。按以下规范写「公司文档初始化项目」需求文档的第二章与第三章：

【第二章 高层级需求】
- 只写高层级需求 HL-01~04，不下钻子特性。
- 每条 HL 包含 6 项属性：Requirement ID / Priority / Target Release / Change History / 对应 Feature/Sub-feature / 是否可测试(Testable)。
- 6 项属性**必须用两列表格（list-table + :header-rows: 0）呈现**，格式见规范；禁止逐行加粗内联写法。
- 属性表后用一段描述该 HL 的目标与范围。
- 是否可测试取值：可测试 / 部分可测试 / 不可测试；不可测试须写替代验证方式。

【第三章 高层级需求的拆分】
- 3.1 为「高层级需求 ↔ 底层级需求 映射表」(list-table)：列=需求编号 / 高层级需求 / 底层级需求(LL) / 大致内容。
- 3.2 为每个底层级需求 LL-00x 写一节，含：①6 项属性（两列表格形式，含是否可测试） ②场景描述 ③模块职责表。
- 模块职责表列=模块 / 需要做什么 / 前提条件 / 触发条件 / 执行结果。
- 标准 9 模块逐模块填写（研发部/测试质量部/产品部/运维SRE/市场售前/客户支持/管理层PMO/HR新人培训/技术写作组(Owner)）；
  无关模块填「否（无职责）/ — / — / —」。主责模块标（主）。
- 明确「在什么条件下触发了什么、产生什么结果」。
- 是否可测试验收点示例：可测试=存在检查/演示/用例；部分可测试=核心可验、效果定性；不可测试=需写替代度量。

【通用约束】
- 属性与工时为示例估算口径，必须标注「示例口径、绝不编造」。
- 保持与已有 Feature/Sub-feature 编号一致。
```
