# 需求文档书写规范与提示词（company_doc_init 适用）

> 本文档沉淀「公司文档初始化项目」**第二章（高层级需求）** 与 **第三章（需求详细设计）** 的书写规范，
> 可作为可复用提示词直接喂给 AI 生成/重写对应章节。示例取自 `company_doc_init.rst` 与 `company_doc_init_spec.rst`。
>
> **2026-10-15 修订（本版为准）**：第三章由「底层级需求（LL）拆分」改为「**按高层级需求（HL）逐条设计 + 按角色展开**」。
> 小项目不再把 HL 拆成 LL，直接以 HL 为设计粒度；HL↔LL 映射表与 LL 模块职责表仅作 **demo 参考（大项目才用）**。
> 与旧版冲突处，以本版为准。

---

## 1. 目的

统一需求文档写法，保证文档可读、可评审、可追踪、**可验收**：

- **高层级需求（HL）的声明**（第二章）；
- **每条 HL 的逐角色设计**（第三章）：每个参与角色写清「职责 / 前置条件 / 交付物」与「风险与解决办法」；
- （大项目可选）HL → LL 拆分与 LL 模块职责（仅 demo，见 §5.4）。

## 2. 概念层级

- **高层级需求 HL（Epic）**：项目级目标，本例 4 条（HL-01~04）。**小项目直接以 HL 为设计粒度，不再拆 LL。**
- **Feature / Sub-feature**：交付物/能力桶。文档类型特性 Feature-A~F；流水线子特性 HL-03-A~F。
- **底层级需求 LL（可选）**：大项目才拆的粒度。本例保留 HL↔LL 映射表 **仅作 demo 参考**，不实际下钻。

## 3. 通用属性（HL 必须包含）

下列 6 项属性 **必须包含**，且 **统一用「两列表格（list-table，header-rows: 0）」呈现**，不得使用逐行加粗内联写法。

| 属性 | 说明 | 取值示例 |
| --- | --- | --- |
| Requirement ID | 唯一编号（HL-01 / LL-001） | HL-01 / LL-001 |
| Priority | 优先级 | P0 / P1 / P2 |
| Target Release | 目标版本/季度 | R1 / R2 / R3 |
| Change History | 版本与日期 | v1.0 初稿 2026-10-15 |
| 对应 Feature / Sub-feature | 引用的 feature 或 sub-feature 编号 | Feature-A / HL-03-A |
| 是否可测试（Testable） | 该需求是否可被验证/验收；不可测试需说明原因或替代验证方式 | 可测试 / 部分可测试 / 不可测试 |

**两列表格格式（强制）**：

```rst
.. list-table:: <Requirement ID> 属性
   :header-rows: 0
   :widths: 32 68

   * - Requirement ID
     - HL-01
   * - Priority
     - P0
   * - Target Release
     - R1（2026-Q4）
   * - Change History
     - v1.0 初稿（2026-10-15）
   * - 对应 Feature/Sub-feature
     - Feature-A / B / C / D / E / F
   * - 是否可测试
     - 可测试
```

> 表格必须放在需求标题（HL-x 或 3.2.x 小节标题）之后、目标/场景描述之前；
> 表格前后各保留一个空行。`<Requirement ID>` 替换为该需求真实编号（如 `HL-01 属性` / `LL-001 属性`）。

> **是否可测试（Testable）取值约定**
> - **可测试**：存在明确验收条件，可通过检查/演示/用例验证（如"站点可访问且目录 lint 通过"）。
> - **部分可测试**：核心交付物可验证，但部分效果只能定性（如 onboarding 的 ramp-up 周期靠问卷反馈）。
> - **不可测试**：纯目标性/原则性陈述，需在备注写替代度量方式或删除该需求。

## 4. 第二章写法（高层级需求）

- 只列 HL 需求，**不下钻**子特性/底层级需求（下钻放到第三章）。
- 每条 HL 结构：先「6 项属性（两列表格）」，再一段**目标描述**（做什么 + 范围）。
- 属性**必须**用两列表格（`list-table` + `:header-rows: 0`）呈现，禁止逐行加粗内联写法（见 §3）。

## 5. 第三章写法（需求详细设计，按 HL 展开）

### 5.1 3.1 概览

#### 5.1.1 3.1.1 映射表（demo）

- 用 `list-table`，列：**需求编号 | 高层级需求 | 底层级需求(LL) | 大致内容**。
- 一行 HL 对应一行 LL 编号（空格分隔）。
- **仅作 demo 参考**：小项目不实际下钻 LL，直接以 HL 写设计；映射表后应加一句说明「本项目较小，直接按 HL 写设计」。

#### 5.1.2 3.1.2 角色与工时

- 用 `list-table`，列：**编号 | 高层级需求 | 受影响角色（主责标「主」）| 可能工时(人日)**。
- 只列**有职责**的角色，无职责 / 仅消费的角色不列；主责标「（主）」，全局 Owner 标「(Owner)」。
- 工时为**示例估算口径（理论下限）**，需标注「中位预期约 2 倍、兼职岗 2-2.5 倍」，并尽量对齐既有工期档位。

### 5.2 3.2 每条 HL 详述

每个 HL 一节（`3.2.x`），固定三段：

1. **属性块**（6 项通用属性，两列表格，见 §3）
2. **场景描述**（1~2 段：为什么做、解决什么问题、**涉及哪些角色**）
3. **逐角色小节**（`3.2.x.y`）：每个参与角色独占一个子标题，**不参与的角色不写**

### 5.3 角色小节（3.2.x.y）结构

每个角色小节固定两块（用加粗小标题 + 列表格，**不再往下分节**）：

1. **职责 / 前置条件 / 交付物**——两列表（header-rows: 0），三行：职责 / 前置条件 / 交付物；
2. **风险与解决办法**——两列表（header-rows: 1），列：**风险 / 问题 | 解决办法**。

```rst
3.2.1.1 技术写作组（Owner）
++++++++++++++++++++++++++++++++++++++++++++++++

**职责 / 前置条件 / 交付物**

.. list-table::
   :header-rows: 0
   :widths: 20 80

   * - 职责
     - 选型并搭建 Git 仓库 + Sphinx 站点骨架；制定目录树与命名规范；定义三级权限模型。
   * - 前置条件
     - 管理层批准平台选型与预算。
   * - 交付物
     - 统一存储上线、目录规范 v1.0、权限模型、接入指南。

**风险与解决办法**

.. list-table::
   :header-rows: 1
   :widths: 34 66

   * - 风险 / 问题
     - 解决办法
   * - 权限落在托管层，敏感文档可能误入公开仓库
     - 三级权限由 nginx + SSO 落地；敏感文档不直接提交公开仓库
```

### 5.4（可选，大项目才用）底层级需求详述（LL）

- 仅当项目大、确有 HL→LL 拆分需求时启用；小项目跳过，映射表保留 demo 即可。
- 每个 LL 一节：属性块（6 项）+ 场景 + **模块职责表**。
- 模块职责表列：**模块 | 需要做什么 | 前提条件 | 触发条件 | 执行结果**。
- 标准 9 模块（**须逐模块填写**；无关模块填 `否（无职责） / — / — / —`）：
  研发部 / 测试质量部 / 产品部 / 运维SRE / 市场售前 / 客户支持 / 管理层PMO / HR新人培训 / 技术写作组(Owner)。
- 主责标「（主）」。

## 6. 复用提示词（直接喂给 AI）

```text
你是技术写作工程师。按以下规范写「公司文档初始化项目」需求文档的第二章与第三章：

【第二章 高层级需求】
- 只写高层级需求 HL-01~04，不下钻子特性。
- 每条 HL 包含 6 项属性：Requirement ID / Priority / Target Release / Change History / 对应 Feature/Sub-feature / 是否可测试(Testable)。
- 6 项属性必须用两列表格（list-table + :header-rows: 0）呈现；禁止逐行加粗内联写法。
- 属性表后用一段描述该 HL 的目标与范围。
- 是否可测试取值：可测试 / 部分可测试 / 不可测试；不可测试须写替代验证方式。

【第三章 需求详细设计（按高层级需求展开）】
- 本项目较小，不拆底层级需求（LL），直接以 HL 为粒度写设计。
- 3.1.1 为「高层级需求 ↔ 底层级需求 映射表」(list-table)：列=需求编号 / 高层级需求 / 底层级需求(LL) / 大致内容；
  仅作 demo 参考，表后注明「本项目较小，直接按 HL 写设计」。
- 3.1.2 为「各 HL 受影响角色与大概工时」(list-table)：列=编号 / 高层级需求 / 受影响角色（主责标「主」）/ 可能工时(人日)；
  只列有职责角色；工时为示例估算口径（理论下限，中位预期约 2 倍）。
- 3.2 为每个高层级需求 HL-01~04 写一节，含：①6 项属性（两列表格，含是否可测试）②场景描述（含涉及角色）③逐角色小节。
- 逐角色小节（3.2.x.y）：每个参与角色独占一个子标题，不参与的角色不写；
  每角色固定两块：①职责/前置条件/交付物（两列表，header-rows:0，三行）②风险与解决办法（两列表，列=风险/问题 | 解决办法）。
- 属性与工时为示例估算口径，必须标注「示例口径、绝不编造」。
- 保持与已有 Feature/Sub-feature 编号一致。
```

## 8. 与 HLD 书写规范的边界

| 维度 | 需求详细设计（本规范） | 高层级设计 HLD（hld/hld_writing_guide.md） |
| --- | --- | --- |
| 视角 | 需求视角：谁做什么 / 前置 / 交付 / 风险 | 设计视角：架构、时序、工具、脚本 |
| 粒度 | 每条 HL → 每个参与角色 | 每条 HL 一页（模块交互 + 角色输入输出） |
| 交付 | 可验收的角色职责与风险对策 | 可落地、可评审的实现方案 |

两者通过 **Feature ref / HL 编号** 挂钩；需求详细设计先定义「谁做什么、有什么风险」，HLD 再落「怎么做、用什么工具」。
