竞品文档体系调研报告

对象：曦望 Sunrise（GPGPU 软件栈，商汤分拆）· 市场技术选型分析 · 调查员视角

调研日期：2026-10-15 · 样本：19 家 GPGPU / AI 芯片 / 相关半导体软件栈公司（≥15 家达标）

核心结论速览：19 家样本中，真正把文档当"工程资产"、用文档即代码（Sphinx/Docusaurus 等 SSG）托管公开站点的是少数；多数国产 GPGPU 同行（壁仞、天数智芯、瀚博、海光）停留在 SPA 门户 + PDF/SDK 分发 阶段，没有可机读的 API 符号级文档。具备符号级 Sphinx（C/C++ 域可跨文档引用）的仅有 NVIDIA 与 燧原 两家；寒武纪、AMD 的 Sphinx 以指南/术语级为主（API 参考另行构建）。对曦望而言，最对标的不是"国产门户派"，而是 NVIDIA / 燧原 / 寒武纪 / AMD 这一"工程规范派"。

一、调研方法论（与"摩尔线程 / 沐曦"同口径）

每家文档站均经过指纹探查，而非仅凭官网文案判断。判定手段：

  • Sphinx 判定：探测 objects.inv。真 Sphinx 站点返回 # Sphinx inventory version 2 头 + zlib 压缩体；解压后统计 domain:role 分布——c:function/cpp:function 等存在即"符号级"，全为 std:doc/std:term 即"章节/术语级"。
  • 现代 SSG 判定：读 <meta name="generator"> 与 JS 包名（Docusaurus / Rspress / GitBook / Next.js）。
  • 反伪造要点（关键）：SPA 门户常用"兜底路由"对任何路径返回 200 + HTML，导致 /objects.inv 也返回 200。本报告对海光、壁仞、天数智芯、瀚博的 objects.inv 实测返回的是 HTML 页面而非 Sphinx 清单——由此证伪"Sphinx"，还原为"门户 + PDF"。产物指纹只能证伪、不能证真，故凡未直接取到真清单/生成器标识的，一律标注置信度。
  • 不编造原则：网络不可达（Graphcore）或信息未公开（景嘉微/黑芝麻/昆仑）者，如实标注"未确认/无公开站"，不下结论。

形态 A — 符号级 Sphinx（API 可机读、可跨文档引用，docs-as-code 标杆）

成员：NVIDIA、燧原。

判定证据：NVIDIA objects.inv 解压得 4658 条，其中 cpp:enumerator 1722 / cpp:functionParam 1529 / cpp:function 561 / cpp:member 495 / c:macro 97 …；燧原 objects.inv 解压得 1295 条，cpp:enumerator 707 / cpp:function 249 / cpp:functionParam 209 / cpp:class 56 …。参数(209/1529) > 函数(249/561)——说明连单个参数都可被引用，是真正的符号级图谱。

含义：这是 GPGPU 厂商最该追求的"真参考对象"。代价是需要 Doxygen + Breathe 或 hawkmoth 抽取 C/C++ 语法树，工程门槛最高，但一旦建成，API 文档与代码同源、可校验、可跨页 :ref:。

形态 B — 章节/术语级 Sphinx（指南/术语为主，API 参考多另行构建）

成员：寒武纪、AMD ROCm、沐曦（后端内核）。

判定证据：寒武纪编程指南子项目 objects.inv 全为 std:doc（章节级，无 C/C++ 域）；AMD ROCm 抽样为 std:term（术语级）。二者均为真 Sphinx，但抽样构建不含 API 符号——其 HIP / CNCC / Runtime 等 API 参考多为独立构建（本次未逐一枚举，不臆测符号数）。沐曦后端 Sphinx 经 pandoc 链路：既有调查确认其 searchindex.js 中 c:/cpp: 域符号数为 0（pandoc 只转格式、不产 .. c:function::），属"用 Sphinx 却没拿到符号域"的反例。

含义：Sphinx 不等于符号级；"用没用 Breathe/Doxygen"才是分水岭。沐曦证明"门户化 ≠ 文档生成"，不可作为"Sphinx 也可以不上 Breathe"的先例。

形态 C — 现代 Markdown SSG（前端框架渲染，无符号域，偏产品/生态站）

成员：摩尔线程（Docusaurus v3.10.1 + 自建渲染层）、地平线（Rspress v2.0.6）、平头哥/玄铁（GitBook 3.2.3 开源版）。

判定证据：摩尔线程 docs.mthreads.com 生成器标识 Docusaurus v3.10.1，developer.mthreads.com 为 Next.js（双层结构）；地平线 doc.oe.horizon.auto 生成器标识 Rspress v2.0.6；平头哥 yoc.docs.t-head.cn 生成器标识 GitBook 3.2.3。

含义：这类框架源是 Markdown/MDX，渲染快、对产品/市场团队友好、搜索与导航体验好，但无 objects.inv、无 C/C++ 符号域——本质是"散文文档站"，不是"API 参考引擎"。摩尔线程的"自建渲染层"是对 Docusaurus 默认能力不足的补丁（既有调查已确认其 178 个函数签名被渲染成带四层章节号的 h4 全进 TOC、零示例代码）。

形态 D — 企业 SPA 门户 + PDF/SDK 分发（非 SSG，inv 证伪 Sphinx）

成员：壁仞、天数智芯、瀚博、海光。

判定证据：四家均在子域提供"开发者社区/中心"（壁仞 developers.birentech.com、天数智芯 developer.iluvatar.com + support.iluvatar.com PDF 中心、瀚博 developer.vastaitech.com、海光 csp.hygon.cn + 光合社区）。对四家根路径 /objects.inv 实测均返回 HTML 页面（SPA 兜底路由），而非 Sphinx 清单——确证它们不是 Sphinx 静态站。文档实质以 PDF 下载 / SDK 包内文档（海光 DTK 含 PDF/HTML/MD）形式分发。

含义：这是当前多数国产 GPGPU 同行的"务实现状"：文档被当交付物(文件)而非工程资产(站点)。优点是门槛低、可控；缺点是不可检索、不可跨页引用、版本易失真、无 API 机读。曦望若只看这些同行，会低估文档工程化投入。

形态 E — 自研 / 定制文档平台

成员：华为昇腾（hiascend.com/document）、Intel oneAPI（intel.com/docs）。

判定证据：华为文档页无 Sphinx/Docusaurus/Rspress/Next.js 生成器标识，objects.inv 返回 301（非 Sphinx），是独立研发的文档系统（体量巨大、强权限/版本/多产品矩阵）。Intel oneAPI 为 intel.com 自研 CMS，版本化手册 + PDF，无标准 SSG 特征。

含义：只有华为/Intel 这种体量(且有自研平台团队)才养得起自研文档中台。对曦望（首任 TW、从零建体系）不具可复制性——自研是"别人烧过钱的结果"，不是起点。

形态 F — 无独立公开文档站（PDF / SDK / 第三方框架 / 社区仓库）

成员：景嘉微、黑芝麻、百度昆仑、龙芯（半）、Graphcore（待定）。

  • 景嘉微：官网为营销站，无开发者门户；文档为 OpenCL 用户手册等 PDF / 随驱动包（公开资料仅见社区转载）。
  • 黑芝麻：官网以"山海工具链"产品页为主，文档随 SDK（PDF / 参考手册）提供，无公开检索站。
  • 百度昆仑：无独立文档门户，XPU 适配文档全部寄生在飞桨 PaddlePaddle 文档站（paddlepaddle.org.cn/hardware_support/xpu）。
  • 龙芯：指令集/ABI 文档以 PDF/HTML 在 GitHub LoongArch-Documentation releases 发布；loongnix.cn 为社区门户（SPA，框架未识别）。无标准 SSG 站点。
  • Graphcore：URL 结构（/projects/<name>/en/<ver>/overview.html）强烈疑似 Sphinx 版本化项目，但本报告窗口内 WebFetch 与 curl 均因 TLS/网络不可达，暂标"疑似 Sphinx，待复测"，不下定论。

四、对曦望 Sunrise 的选型启示

结合本作品集既有选型结论（Sphinx 86.4 : Docusaurus 70.2，前提＝已配备专职文档岗）与本次竞品实况：

  • 对标要选对群：曦望作为 GPGPU 软件栈厂商，真正的可比对象是"工程规范派"——NVIDIA、燧原、寒武纪、AMD。它们要么是符号级 Sphinx（NVIDIA/燧原），要么是章节级 Sphinx（寒武纪/AMD）。国产"门户+PDF 派"（壁仞/天数/瀚博/海光）是现状而非标杆，若以此为目标会显著低估文档工程化投入。
  • Sphinx + Breathe/Doxygen 是"像 NVIDIA 一样做 API 文档"的唯一已验证路径：若要 C/C++ 符号级引用（参数都可被引），必须回到"上游抽取 Doxygen XML → Breathe → Sphinx"，不能靠 pandoc（沐曦已证伪）；纯 C 注释可统一则可用 hawkmoth。这与既有报告"选哪些工具由真源是什么决定"一致。
  • Docusaurus/Rspress 适合做"产品与生态站"而非"API 参考引擎"：若曦望想给市场/生态一个体验好的站点，可参考两种已验证的"双层"范式——摩尔线程（docs 用 Docusaurus、developer 用 Next.js，并自建渲染层补 API 短板）与沐曦（Next.js 门户 + 后端 Sphinx 内核，源 reST）；但二者各有隐性成本：摩尔线程的"自建渲染层补丁"（Docusaurus 无符号域、需手动兜底）与沐曦的 pandoc 链路（符号域=0、丢了 API 可机器引用性）。真正要"符号级 API 可引用"，仍应走 Sphinx + Breathe/Doxygen 这条已验证路径。
  • 自研平台（华为/Intel）现阶段不碰：曦望是首任 TW、从零起步，自研文档中台是"终点"不是"起点"。
  • 最该避免的，是"门户 + PDF"陷阱：它是多数国产同行的现状，但牺牲了可检索、可引用、可版本化、可机读——恰恰是曦望作为 GPGPU 厂商区别于"只卖卡"的差异化资产所在。

数据来源与方法：本报告所有框架结论均来自对目标文档站的实时指纹探查（curl / objects.inv zlib 解压 / generator meta 解析），未引用任何未核对的二手描述。符号级统计口径为 c:function/cpp:function/cpp:enumerator/cpp:functionParam/cpp:class/c:member/cpp:enum/c:macro 等 C/C++ 域条目数。本调研与 tw-portfolio 作品集中《Sphinx vs Docusaurus 选型报告》《摩尔线程 / 沐曦 行业对标》章节同口径，结论互补。
