## 1. 结论

| 候选方案 | 能力分（满分 100） | 判定 |
| --- | --- | --- |
| **Sphinx** | **86.4** | **采纳** |
| Docusaurus | 70.2 | 备选，本期不采纳 |

**一句话**：Sphinx 赢在**内容生产能力**——能不能自动产出 API 手册、PDF、可机器校验的引用；
Docusaurus 赢在**读者体验**——页面好不好看、导航顺不顺、上手快不快。
本项目的需求压在"内容生产能力"这一侧，所以选 Sphinx。

## 2. 差距分析

### 2.1 差多少

| 计算口径 | Sphinx | Docusaurus | 差距 |
| --- | --- | --- | --- |
| 基准（已配备专职文档岗） | 86.4 | 70.2 | **+16.2** |
| 场景 A · 文档含内部信息 | 86.4 | 70.2 | +16.2 |
| 场景 B · 文档不含内部信息 | 82.2 | 76.6 | +5.6 |
| 5–10 年后（AI 时代重估） | 89.2 | 66.2 | **+23.0** |
| 把"要不要花钱"一起算 · 场景 A | 87.2 | 73.1 | +14.1 |
| 把"要不要花钱"一起算 · 场景 B | 85.1 | 86.3 | −1.2（Docusaurus 反超） |

**读法**：只要文档**含内部信息**，Sphinx 在能力与成本上**同时领先**，结论无争议；
只有把范围收窄成"纯对外 + 不要 PDF + 没有 C/C++ API + 没有专职文档岗"时，
Docusaurus 才会反超——**"脱敏"本身不足以翻转结论**。

### 2.2 差在哪（三条，都不需要技术背景）

| # | 差距点 | 这意味着什么 | 结果 |
| --- | --- | --- | --- |
| 1 | **API 手册能不能自动生成** | 几百个 C/C++ 接口，靠人手抄签名与参数必然出错、必然过时 | Docusaurus 只能拿到一半分，且无现成补齐路径 |
| 2 | **能不能出 PDF / 离线包** | 内网审计与客户常要一个可归档的离线件 | **Docusaurus 侧没有补齐路径**（硬伤） |
| 3 | **跨文档引用能否机器校验** | 接口或术语改名后，能否自动发现"哪里引用失效了" | Sphinx 独有；Docusaurus 需自建 |

**反过来看，Docusaurus 领先的只有 2 项**——多版本文档、导航体验，
**都在"外观与前端"层，可以换主题追**；而它的短板（PDF、API 自动生成）**补不了**。
这就是"可替代性不对称"：它的领先可以买，它的落后买不到。

### 2.3 差距稳不稳

把评分权重往**最不利于 Sphinx** 的方向极端调整，Docusaurus **仍落后 5.2 分**；
把时间尺度拉到 5–10 年，差距**从 16.2 扩大到 23.0**。**结论不翻转。**

## 3. 代价、成本、周期

| 决策者的问题 | 直接答案 |
| --- | --- |
| **要花钱吗** | 三套工具本体**都免费**。**文档公开 → 可零现金成本；文档含内部信息 → 必然产生权限与托管支出**。付费的真正驱动因素是"内容是否对外"，不是工具 |
| **要付出什么代价** | 写作语法门槛略高（用专职岗消化）、多版本能力靠第三方插件（选型时已评估缓解方案） |
| **多久能用起来** | 骨架可用 **1.5–2 周**；**基础可用 5–6 周**（推荐起步档）；完整能力（多版本 / 权限分级 / PDF）**8–10 周** |
| **谁来做** | **1 名专职文档工程师**（约 27 人日）——本报告就是按"有这个岗"算分的 |
| **谁必须配合** | ① **研发负责人**：定文档仓库结构；② **研发工程师**：把头文件注释补齐（最关键，补不上则 API 页是空壳）；③ **运维**：给构建机与内网镜像 |

## 4. 什么时候要回头重审

以下条件满足 **≥3 条**，本结论就需要重估：

| # | 改判条件 |
| --- | --- |
| 1 | 文档只对外、无机密分级需求 |
| 2 | 不需要 PDF / 离线交付件 |
| 3 | API 以 REST / GraphQL / TS / Python 为主，**无大规模 C/C++ 头文件** |
| 4 | 需要交互式 demo / playground，或要与官网、博客同站 |
| 5 | 维护者是**无专职技术写作岗**的前端 / 全栈团队 |
| 6 | 需要开箱即用的多版本文档托管 |
