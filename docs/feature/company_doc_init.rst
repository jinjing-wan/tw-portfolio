1.1 项目背景与目的
~~~~~~~~~~~~~~~~~~~

公司当前的技术文档散落在 wiki / 网盘 / 个人电脑：无版本、无评审、无检索、无权限，
知识沉淀在个别老员工脑子里，新人入职后看不懂、接不上，交付与协作高度依赖口口相传。

本项目的目的是把"人脑里的知识"变成"统一库 + 规范 + 流水线 + 可检索"的公司资产——建立
集中文档库（单一信息源 Single Source of Truth）、统一模板与规范、Docs-as-Code 评审发布流水线，
并完成存量迁移与新人 onboarding。

2.1 方案选型：为什么选它，为什么不选其余
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

2.1.1 最终方案
^^^^^^^^^^^^^^^^

**最终方案：以 Sphinx 为文档生成内核、以自建最小门户为入口的「内核 + 门户」两层方案。**

架构形态参照同业公开文档站的做法（三家 GPU 厂商的文档栈实测对照见 2.1.3），
但 **只参照架构、不参照其内容生产方式** ——内容一律走自动抽取链，不手工搬运。

.. list-table:: 最终方案的三层结构与选用物
   :header-rows: 1
   :widths: 18 28 54

   * - 层次
     - 选用物
     - 在方案里承担什么
   * - 内容生产层（抽取）
     - Doxygen（``GENERATE_XML=YES``）+ Breathe
     - 从头文件注释自动抽出结构信息，直接产出 **带 C/C++ 符号域** 的 API 参考页。纯 C 且注释可统一为 reST 时，可改用 hawkmoth 省去 Doxygen 环节
   * - 内容生成层（内核）
     - Sphinx + MyST-Parser
     - 唯一构建内核：一份源文件同时出 HTML / PDF（LaTeX）/ 跨项目符号表 ``objects.inv``；Markdown 与 reST 可混写
   * - 门户与托管层（入口）
     - Next.js 最小门户（可后置）+ 内网静态站 + CI
     - 提供检索、文档分类筛选与下载入口；权限分级落在此层。起步阶段可先用 Sphinx 自带静态站，门户后置

**三句话说明为什么是它：**

1. 本项目的诉求压在 **"生产"** 一侧——几百个接口要随代码同步更新、还要给内网出可归档的离线件；
2. 组织前提是 **已配备专职文档岗** ——专职岗消化 Sphinx 的语法与引用体系学习成本，同时放大它"符号可引用"的长板；
3. 只需 **一份真源、两个发布目标**，即在线站点与离线归档件两种交付物，不必为不同受众维护第二套工具链。

   * - 收窄场景（文档不含内部信息）
     - 82.2

     - +5.6

     - Sphinx +14.1

**读法**：只要文档 **含内部信息**，Sphinx 在 **能力与成本上同时领先**；只有把范围收窄成
"纯对外 + 不要 PDF + 没有 C/C++ 接口 + 没有专职文档岗"，Docusaurus 才会反超（85.1 : 86.3）。
**只做脱敏，不足以翻转结论。**

三条硬差距（决定性的三项）：

.. list-table:: 与备选方案的硬差距
   :header-rows: 1
   :widths: 6 24 44 26

   * - #
     - 差距点
     - 对本项目的直接影响
     - 备选侧能否补齐
   * - 1
     - API 参考能否 **自动生成**
     - 几百个接口靠人手抄签名与参数，必然出错、必然过时
     - Docusaurus 侧无现成补齐路径（MDX 生态没有 Breathe 等价物）
   * - 2
     - 能否出 **PDF / 离线包**
     - 内网审计与客户交付常要可归档的离线件
     - 补不了（属硬伤）
   * - 3
     - 引用能否 **机器校验**
     - 接口或术语改名后，能否自动发现"哪里引用失效"
     - Sphinx 独有（跨项目符号级引用）

**结论稳不稳**：把权重往 **最不利于 Sphinx** 的方向极端调整，Docusaurus 仍落后 **5.2 分**；
要让结论翻转，需把单一维度权重提到基准的 4 倍以上（约 24），并同时把三条硬差距压到合计近 0，
已超出可辩护区间；**结论不翻转。**

2.1.3 为什么不选其余方案
^^^^^^^^^^^^^^^^^^^^^^^^^^

.. list-table:: 候选方案与不选它的主因
   :header-rows: 1
   :widths: 16 14 46 24

   * - 候选
     - 判定
     - 不选它的主因
     - 差距能否补齐
   * - **Sphinx**
     - **采纳**
     - 唯一同时满足"接口自动生成 + PDF/离线件 + 引用机器校验"三项的一条路
     - —
   * - Docusaurus
     - 备选，本期不采纳
     - 它领先的只有两项—— **多版本文档** 与 **导航体验**，都属 **外观层**，换主题即可追；而它落后的 PDF 与 API 自动生成是 **买不到** 的。MDX 生态 **没有符号域机制**，也没有 Breathe 等价物，要自建渲染层且仍拿不到符号级引用
     - 不可补齐
   * - MkDocs（Material 主题）
     - 不采纳
     - 同为静态站生成器，但 **缺 C/C++ 符号域与跨项目符号图**，PDF 依赖第三方插件、不在主链上；Material 高级特性属付费档（Insiders 约 $15/月起）
     - 不可补齐
   * - GitBook
     - 不采纳
     - SaaS 托管形态：**内网不可用**，无法接自动抽取链，无符号域；离线归档件与分级权限均受平台能力限制
     - 不可补齐
   * - Read the Docs（SaaS 托管平台）
     - 不采纳为平台，仅留作托管候选
     - 它本身不是生成器；且 **私有仓库、SSO、文档鉴权都属付费项**：Business 约 $50 / $150 / $250 每月，Enterprise $10k 起/年，内网场景用不上
     - 付费可补，但成本不可控
   * - 现状（wiki / 网盘 / 个人电脑）
     - 明确排除
     - 无版本、无评审、无检索、无权限——本项目要解决的正是它
     - —

.. note::
   上表中 **Docusaurus 是唯一进入完整评分对照的备选**；MkDocs / GitBook / Read the Docs 属 **能力判据排除**
   （按官方公开能力清单比对），未进入逐维评分。

架构形态的参照对象，来自三家同业文档栈的同口径实测：

.. list-table:: 同业文档栈三形态对照（架构选型参照）
   :header-rows: 1
   :widths: 16 22 38 24

   * - 同业
     - 文档栈形态
     - 关键实测证据
     - 对本方案的含义
   * - NVIDIA（CUDA Runtime API）
     - Sphinx + Breathe + Doxygen
     - 解压 ``objects.inv`` 得 **4,657 个 C/C++ 域符号**，其中参数 1,529 个、多于函数 561 个，且目标路径保留 Doxygen 分组名；对照的编程指南为 0 个编程域符号
     - **API 抽取链照它做**：这是"符号级"的验收基准，而非厂商规模差异
   * - 摩尔线程（MUSA）
     - Docusaurus + 自建渲染层
     - 该栈 **不存在** ``objects.inv`` 机制；已知规模参照（LLVM 两万余页）在 Docusaurus 上构建失败/内存爆炸，需放大 Node 内存
     - 反面印证：前端选 MDX，就得自建渲染层，且仍拿不到符号域——这笔债应计入前端选型成本
   * - 沐曦（MXMACA）
     - Sphinx 内核 + 自建 Next.js 门户（源文件经 pandoc 转为 reST）
     - ``objects.inv`` 共 471 条，其中 **456 条是"通用章节名 + 序号"、C/C++ 域符号 0 个**；178 个函数签名被渲染成带四层章节号的 h4 全进目录；``searchindex.js`` 的对象索引为空
     - **只参照它的架构（内核 + 门户），不参照它的内容生产**：pandoc 中转会把函数签名降级成纯文本，符号语义在链路中段即被抹掉
