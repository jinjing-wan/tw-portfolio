## 总体架构

最终方案为「**内核 + 门户**」两层结构：以 **Sphinx 为文档生成内核**、以 **自建最小门户为入口**。架构形态参照三家同业 GPU 厂商公开文档站的做法，但 **只参照架构、不参照其内容生产方式**——内容一律走自动抽取链，不手工搬运。
[来源：company_doc_init.rst §2.1.1]

三层结构与选用物：

| 层次 | 选用物 | 在方案里承担什么 |
| --- | --- | --- |
| 内容生产层（抽取） | Doxygen（`GENERATE_XML=YES`）+ Breathe | 从头文件注释自动抽出结构信息，直接产出 **带 C/C++ 符号域** 的 API 参考页 |
| 内容生成层（内核） | Sphinx + MyST-Parser | 唯一构建内核：一份源文件同时出 HTML / PDF（LaTeX）/ 跨项目符号表 `objects.inv`；Markdown 与 reST 可混写 |
| 门户与托管层（入口） | Next.js 最小门户（可后置）+ 内网静态站 + CI | 提供检索、文档分类筛选与下载入口；权限分级落在此层。起步阶段可先用 Sphinx 自带静态站，门户后置 |

[来源：company_doc_init.rst §2.1.1 三层结构表]

工具链全景（数据流向）：

```text
头文件注释 ──Doxygen(GENERATE_XML)──> XML ──Breathe──> Sphinx 的 C/C++ 域指令
                                                       │
Markdown / reST 源 ────────────────────────────────────┤
                                                       ▼
                                 Sphinx 构建（HTML / PDF / objects.inv）
                                                       │
                                 CI 门禁（构建 0 告警 + 死链 + 元数据必填）
                                                       ▼
                                 内网静态站 ──>（可选后置）Next.js 最小门户
```

[来源：company_doc_init.rst §2.2.1.1 工具链全景]

**三句话说明为什么是它**：① 本项目诉求压在「生产」一侧——几百个接口要随代码同步更新、还要给内网出可归档的离线件；② 组织前提是 **已配备专职文档岗**，消化 Sphinx 学习成本并放大「符号可引用」长板；③ 只需 **一份真源、两个发布目标**（在线站点与离线归档件），不必为不同受众维护第二套工具链。
[来源：company_doc_init.rst §2.1.1]

## 接口与依赖

**内部数据流接口（符号如何被引用）**

1. Doxygen 解析头文件注释 → 输出 `XML`（**必须 `GENERATE_XML=YES`，不能只出 HTML**）。
2. Breathe 读取 XML → 渲染为 Sphinx 的 `c:` / `cpp:` 域指令，符号自此可被 `:ref:` / `objects.inv` 跨页、跨项目引用。
3. Sphinx 统一构建：Markdown（MyST）/ reST 源与 `c:`/`cpp:` 指令汇入同一份构建，产出 HTML / PDF / `objects.inv`。
4. `objects.inv` 作为跨项目符号表，是「引用机器校验」的基础（接口或术语改名后自动发现失效引用）。

[来源：company_doc_init.rst §2.2.1.1、§2.1.3]

**外部依赖与边界**

| 依赖项 | 说明 | 落在哪一层 |
| --- | --- | --- |
| 内网 PyPI / npm 镜像 | 保证构建机离线可装齐依赖 | CI / 构建环境 |
| nginx / 对象存储 + SSO | 静态站托管与三级权限（公开 / 内部 / 机密）落地 | 门户与托管层 |
| CI 运行环境 | 自托管 Jenkins / GitHub Actions / GitLab CI | 质量门禁层 |
| Next.js 门户 | 检索 / 筛选 / 下载入口，可后置，不阻塞内核上线 | 门户层（后置） |

[来源：company_doc_init.rst §2.2.1.1、§2.2.2.1]

:::{warning}
权限分级落在 **托管层**，Sphinx 构建产物本身不分级。敏感文档若直接提交公开仓库，可能误入公开范围——须由 nginx + SSO 落地三级权限，且入库前过权限检查清单。
[来源：company_doc_init.rst §3.2.1.1 风险]
:::

## 技术决策

### 选型结论：为什么选 Sphinx，为什么不选其余

**最终采纳**：以 Sphinx 为内核 + 自建最小门户的「内核 + 门户」两层方案。这是唯一同时满足「接口自动生成 + PDF/离线件 + 引用机器校验」三项的一条路。
[来源：company_doc_init.rst §2.1.2、§2.1.3]

**量化对照（能力分，满分 100，主场景＝文档含公司内部信息、需分级权限）**：

| 计算口径 | Sphinx | Docusaurus | 差距 |
| --- | --- | --- | --- |
| 基准（已配备专职文档岗，本项目主场景） | **86.4** | 70.2 | **+16.2** |
| 收窄场景（文档不含内部信息） | 82.2 | 76.6 | +5.6 |
| 5-10 年后（AI 时代重估） | 89.2 | 66.2 | **+23.0** |
| 再把「要不要花钱」一并计入（主场景，能力与成本等权） | 87.2 | 73.1 | Sphinx +14.1 |

[来源：company_doc_init.rst §2.1.2 能力分对照]

**三条硬差距（决定性）**：

| # | 差距点 | 对本项目的直接影响 | 备选侧能否补齐 |
| --- | --- | --- | --- |
| 1 | API 参考能否 **自动生成** | 几百个接口靠人手抄签名与参数，必然出错、必然过时 | Docusaurus 侧无现成补齐路径（MDX 生态没有 Breathe 等价物） |
| 2 | 能否出 **PDF / 离线包** | 内网审计与客户交付常要可归档的离线件 | 补不了（属硬伤） |
| 3 | 引用能否 **机器校验** | 接口或术语改名后，能否自动发现「哪里引用失效」 | Sphinx 独有（跨项目符号级引用） |

[来源：company_doc_init.rst §2.1.2 硬差距表]

**结论稳健性**：把权重往最不利于 Sphinx 的方向极端调整，Docusaurus 仍落后 **5.2 分**；要让结论翻转，需把单一维度权重提到基准的 4 倍以上（约 24）并同时把三条硬差距压到合计近 0，已超出可辩护区间——**结论不翻转**。
[来源：company_doc_init.rst §2.1.2]

**候选方案与不选它的主因**：

| 候选 | 判定 | 不选它的主因 | 差距能否补齐 |
| --- | --- | --- | --- |
| Sphinx | **采纳** | 唯一同时满足三项的一条路 | — |
| Docusaurus | 备选，本期不采纳 | 领先的只有多版本文档与导航体验（外观层，换主题可追）；落后的 PDF 与 API 自动生成买不到。MDX 无符号域机制、无 Breathe 等价物 | 不可补齐 |
| MkDocs（Material 主题） | 不采纳 | 缺 C/C++ 符号域与跨项目符号图；PDF 依赖第三方插件、不在主链；Material 高级特性属付费档（Insiders 约 $15/月起） | 不可补齐 |
| GitBook | 不采纳 | SaaS 托管形态：内网不可用，无法接自动抽取链，无符号域 | 不可补齐 |
| Read the Docs（SaaS） | 不采纳为平台，仅留作托管候选 | 本身不是生成器；私有仓库、SSO、鉴权均属付费项（Business 约 $50/$150/$250 每月，Enterprise $10k 起/年），内网用不上 | 付费可补，成本不可控 |
| 现状（wiki / 网盘 / 个人电脑） | 明确排除 | 无版本、无评审、无检索、无权限——本项目要解决的正是它 | — |

[来源：company_doc_init.rst §2.1.3 候选方案表]

:::{note}
Docusaurus 是唯一进入完整评分对照的备选；MkDocs / GitBook / Read the Docs 属 **能力判据排除**（按官方公开能力清单比对），未进入逐维评分。
[来源：company_doc_init.rst §2.1.3 note]
:::

### 同业文档栈三形态对照（架构选型参照）

| 同业 | 文档栈形态 | 关键实测证据 | 对本方案的含义 |
| --- | --- | --- | --- |
| NVIDIA（CUDA Runtime API） | Sphinx + Breathe + Doxygen | 解压 `objects.inv` 得 **4,657 个 C/C++ 域符号**（参数 1,529 > 函数 561），目标路径保留 Doxygen 分组名 | **API 抽取链照它做**：这是「符号级」验收基准，而非厂商规模差异 |
| 摩尔线程（MUSA） | Docusaurus + 自建渲染层 | 该栈 **不存在** `objects.inv` 机制；LLVM 两万余页在 Docusaurus 构建失败/内存爆炸，需放大 Node 内存 | 反面印证：前端选 MDX 就得自建渲染层，且仍拿不到符号域——这笔债计入前端选型成本 |
| 沐曦（MXMACA） | Sphinx 内核 + 自建 Next.js 门户（源文件经 pandoc 转 reST） | `objects.inv` 共 471 条，其中 **456 条是「通用章节名+序号」、C/C++ 域符号 0 个**；178 个函数签名被渲染成带四层章节号的 h4 全进目录；`searchindex.js` 对象索引为空 | **只参照它的架构（内核+门户），不参照它的内容生产**：pandoc 中转会把函数签名降级成纯文本，符号语义在链路中段即被抹掉 |

[来源：company_doc_init.rst §2.1.3 同业对照表]

### 版本兼容与多版本发布策略

- 多版本发布用 **sphinx-multiversion**（或按分支分别构建），按版本并列发布，供不同版本用户查阅。
- 每次发布留快照、可回滚；离线包可从归档取。
- 重大发布走 **Phase Gate**，放行或回滚有据可查。

[来源：company_doc_init.rst §2.2.1.1 多版本/离线件/CI 行、§3.2.3.1 风险]

### 按高层级需求（HL）的落地做法

- **HL-01 建立统一文档库**：Git 为唯一真源，Sphinx 构建静态站；目录按「类型 / 模块 / 版本」三层组织并由 lint 校验；权限三级落在托管层。P0，目标 R1。
- **HL-02 统一规范与模板体系**：六类文档各出一套模板，统一元数据（owner / version / status / 评审记录）并设为必填，进 CI 门禁。P0，目标 R1。
- **HL-03 评审发布流水线**：文档入 Git → PR 评审 → CI 门禁（`sphinx-build -W`）→ 三方评审 → 自动发布 → 多版本并列 → 可回滚。P1，目标 R2。
- **HL-04 存量迁移与 onboarding**：先盘点（留 / 改 / 弃三级判定）→ 按模板迁移入库 → 以手册与 FAQ 产出 3-5 天 onboarding 路径。P1，目标 R3。

[来源：company_doc_init.rst §2.2.2 各 HL 做法]

## 验收标准

> 项目级目标 G1-G4（统一文档库 / 六类模板规范 / Docs-as-Code 流水线 / 存量迁移与 onboarding）的验收口径见 [第 1 章 · 立项报告](executive.md) §2.1，此处不重复列出。本章以下仅列技术侧验收硬指标。

**HL-03 验收硬指标（关键）**：解压 `objects.inv` 后，`c:` / `cpp:` 域符号数 **> 0**，且覆盖该模块 **100% 公开发布符号**；**不能只看「文件是否存在」**——业界已有反例：站点 `objects.inv` 存在、条目 471 条，编程域符号为 0。
[来源：company_doc_init.rst §2.2.2.3 note]

**其余可验证项**：构建 0 告警（`sphinx-build -W` 把告警当错误，死链 / 交叉引用失效 / 标题层级错误在合并前被拦）；三级权限生效；六类模板齐备且元数据必填进 CI；回滚演练成功一次；onboarding 路径 3-5 天可上手。
[来源：company_doc_init.rst §2.2.2.1~§2.2.2.4]

## 风险与应对

| 风险 / 问题 | 解决办法 | 关联需求 |
| --- | --- | --- |
| 注释补齐是最大变量：API 自动生成依赖注释规范 | 模板先行，统一 Doxygen 注释规范并设覆盖率基线；注释补齐由研发侧排期推动 | HL-02 / HL-03 |
| pandoc 位置错，函数签名被降级成纯文本、符号域被抹掉 | pandoc 只做「最后一公里」格式搬运；带语义的 API / 签名必须由抽取链（Doxygen XML + Breathe）提供 | HL-03 / HL-04 |
| 敏感文档误入公开仓库 | 三级权限由 nginx + SSO 落地；敏感文档不直接提交公开仓库，入库前过权限检查清单 | HL-01 |
| 内网构建依赖外网包，装不齐导致失败 | 提前备内网 PyPI / npm 镜像，保证构建机离线可用 | HL-01 / HL-03 |
| SSO 与分组配置复杂、易延期 | 以公司统一认证平台为准；先落公开 / 内部两档，机密档后置 | HL-01 |
| 迁入意愿低、进度慢 | 目录规范明确「单一真源」；未入库的网盘副本不视为正式文档，迁入纳入里程碑考核 | HL-01 |
| 审批环节多、周期长，拖累启动 | 选型材料前置到季度规划会一次过会；预算与权限分级合并评审 | HL-01 |
| 发布不可回滚，事故无法补救 | 每次发布留快照；重大发布走 Phase Gate，放行或回滚有据可查 | HL-03 |
| 该迁的没迁、迁了一堆垃圾 | 盘点覆盖全部存量来源，三级判定「弃」须留理由，避免漏迁关键文档 | HL-04 |
| 对外文档混入内部信息 | 对外文档单独模板 + 发布前脱敏检查，权限分级（HL-01）把关 | HL-02 / HL-04 |
