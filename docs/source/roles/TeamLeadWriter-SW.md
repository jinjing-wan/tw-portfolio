## HL-01 · 建立公司统一文档库（研发部视角）

> 需求属性：Requirement ID HL-01 / P0 / 目标 R1 / 对应 Feature-A~F / 可测试（站点可访问；目录 lint 通过；三级权限生效）。场景：以 Git 仓库为唯一真源、Sphinx 构建静态站，统一「类型 / 模块 / 版本」目录结构与命名规范，落三级权限，作为单一信息源承接全部文档入库。
> [来源：company_doc_init.rst §3.2.1 属性表与场景]

### 职责 / 前置条件 / 交付物

| 项 | 内容 |
| --- | --- |
| 职责 | 按目录规范组织代码相邻文档（HLD / API）目录，并将源文件迁入统一库 |
| 前置条件 | 存储平台与分支规范就绪、目录规范（对应 LL-002）发布 |
| 交付物 | 研发文档源统一纳管、目录一致可检索 |

[来源：company_doc_init.rst §3.2.1.4]

### 风险与解决办法

| 风险 / 问题 | 解决办法 |
| --- | --- |
| 迁入意愿低、进度慢 | 目录规范明确「单一真源」；未入库的网盘副本不视为正式文档，迁入纳入里程碑考核 |

[来源：company_doc_init.rst §3.2.1.4]

## 研发部视角的共性风险与衔接

把四条 HL 里研发部相关风险串起来看，研发部的最大变量集中在两处：① **注释补齐**（HL-02 主责项，直接决定 API 自动生成目标能否落地）；② **迁入意愿与清单完整度**（HL-01 / HL-04，决定统一库与存量迁移的覆盖面）。两者都由研发侧排期与 Owner 牵头核对推动，无法靠文档工具本身解决。

- HL-02 注释规范与覆盖率基线，是后面 HL-03「API 参考可自动生成」（G3 验收项）的前置，须与 [第 2 章 · 技术方案](ManagementWriter.md) 的抽取链（Doxygen XML + Breathe）对齐。
- HL-01 / HL-03 的目录规范与 CI 门禁，把「格式问题不过门禁不进评审」前置，减少研发在评审环节的无效耗时。
- HL-04 的存量清单由 Owner 牵头逐团队核对，研发部配合反查代码库 / 构建产物，避免依赖个人电脑上的散落副本。
