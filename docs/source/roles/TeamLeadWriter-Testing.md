# 第 3.3 章 文档团队负责人（TeamLeadWriter）· 测试质量部视角

:::{note}
本文面向**文档团队负责人（TeamLeadWriter）**，站在**测试质量部**的立场拆解该角色在「公司文档初始化项目」中的职责、交付物与协作接口；不替代技术实现细节，相关技术选型见 [第 2 章 · 技术方案](ManagementWriter.md)、立项背景见 [第 1 章 · 立项报告](executive.md)。

**待确认**：主文档 `company_doc_init.rst` 第 1 章「关键干系人」将文档职责归在 **技术写作组（Owner）** 一条（共 9 类干系人），未单独枚举「TeamLeadWriter / 文档团队负责人」子角色。本页以「团队负责人」视角拆解其职责，事实来源为「技术写作组（Owner）」在各 HL 条目下的职责描述；若后续组织将 TeamLeadWriter 单列为独立干系人，须以最新分工为准。
:::

## 1. 角色定位

文档团队负责人（TeamLeadWriter）是「技术写作组（Owner）」这一干系人的**带队与统筹视角**：既对文档内核与流水线的搭建负责，也对模板规范、发布门禁与回滚把关负责。测试质量部作为**集成测试主管**方参与三方评审，因此与本角色的交集集中在三件事——**模板可测性、步骤可复现、接口文档与实现一致**。

- 技术写作组（Owner）总体定位：搭内核与流水线、定模板与规范、编排内容、把关发布与回滚，交付构建链、模板库、规范、站点。[来源：company_doc_init.rst §2.2.1.2 干系人表]
- 测试质量部总体定位：评审模板可测性与步骤可复现性，作为集成测试主管参与三方评审，校验接口文档与实现一致。[来源：actors_test_qa.md §1、company_doc_init.rst §2.2.1.2]

## 2. 核心职责与测试质量部关注点

下表把「技术写作组（Owner）」职责映射到测试质量部为何要关心它：

| 文档团队负责人职责 | 测试质量部关心的理由 | 来源 |
| --- | --- | --- |
| 选型搭建 Git 仓库 + Sphinx 站点骨架 | 统一真源后，测试文档才能按目录规范组织、被检索（LL-002） | company_doc_init.rst §3.2.1.1 |
| 制定「类型 / 模块 / 版本」目录树与命名规范 | 目录口径一致，是 QA 测试文档「可检索」的前提；口径乱则检索不到 | company_doc_init.rst §3.2.1.1、§3.2.1.6 |
| 定义公开 / 内部 / 机密三级权限模型 | 内部测试结论、缺陷信息若误入公开范围会泄露，须由权限分级兜底 | company_doc_init.rst §3.2.1.1、§3.2.1.1 风险 |
| 编排六类模板与统一元数据，写校验脚本接入 CI 门禁 | 模板是 QA「验收标准可测性」评审的载体；元数据不校验则评审无统一基线 | company_doc_init.rst §3.2.2.1 |
| 把关发布与回滚（Phase Gate） | QA 三方评审结论需可追溯；发布不可回滚则事故无法补救 | company_doc_init.rst §3.2.2.1、§3.2.3 风险 |

## 3. 与测试质量部的协作接口

文档团队负责人与测试质量部的协作集中在以下四个接口，均落在三方评审与模板/迁移流程中：

| 协作接口 | 文档团队负责人提供什么 | 测试质量部在其中做什么 | 来源 |
| --- | --- | --- | --- |
| 三方评审机制 | 组织 PR 评审 + CI 门禁 + 自动发布，使评审可追溯、可回滚 | 作为**集成测试主管**参与三方评审（另两方：领域技术主管、关联模块 Owner），意见留在 PR | company_doc_init.rst §2.2.1.3、actors_test_qa.md §3 |
| 模板可测性评审 | 提供六类模板与统一元数据规范草案 | 评审需求验收标准可测性（LL-004）、HLD 设计可测性（LL-005） | actors_test_qa.md §2、§3 |
| 步骤可复现验证 | 提供用户与操作手册、安装部署模板 | 验证操作步骤可复现（LL-007）、安装环境步骤（LL-008） | actors_test_qa.md §2 |
| 接口文档一致性校验 | 通过 Doxygen + Breathe 抽取链产出带符号域的 API 参考 | 校验接口文档与实现一致（LL-006），提供测试结论（LL-009） | actors_test_qa.md §2、company_doc_init.rst §2.1.2 |

## 6. 风险与应对（测试质量部相关）

| 风险 / 问题 | 对测试质量部的影响 | 解决办法 | 来源 |
| --- | --- | --- | --- |
| 元数据不校验，模板「必填」形同虚设 | QA 评审验收标准可测性时无统一基线 | 元数据必须进 CI 门禁，缺项即构建失败 | company_doc_init.rst §3.2.2.1 风险 |
| 注释补齐是最大变量，API 自动生成落空 | 接口文档与实现一致性难校验，LL-006 受影响 | 模板先行 + 统一 Doxygen 注释规范 + 覆盖率基线，由研发侧排期推动 | company_doc_init.rst §3.2.2.2、§3.2 风险 |
| 发布不可回滚，事故无法补救 | QA 三方评审结论无法追溯、无法回退 | 每次发布留快照；重大发布走 Phase Gate | company_doc_init.rst §3.2.3 风险 |
| 敏感文档误入公开仓库 | 内部测试结论 / 缺陷信息泄露 | 三级权限由 nginx + SSO 落地；敏感文档不入公开库，入库前过权限检查清单 | company_doc_init.rst §3.2.1.1 风险 |
| 目录口径理解不一致 | 测试文档检索不到、迁移漏项 | 目录 lint 脚本统一校验，违规即 CI 失败，倒逼口径一致 | company_doc_init.rst §3.2.1.6 风险 |

[来源：company_doc_init.rst §3.2.1~§3.2.4 风险表、actors_test_qa.md]
