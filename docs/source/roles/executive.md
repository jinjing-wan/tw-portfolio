# 第 1 章 公司文档初始化项目 · 立项报告

:::{note}
本文面向**产品经理与项目负责人**，由「公司文档初始化项目」立项报告（Project Charter）提炼，不展开技术实现细节。所有结论均可回溯至 `company_doc_init.rst` 等主文档；文中示例数据、工时与工期为**示意口径**，非真实承诺，需 PMO 确认后生效。
:::

## 1. 项目背景

公司当前技术文档散落在 wiki / 网盘 / 个人电脑：无版本、无评审、无检索、无权限，知识沉淀在个别老员工脑子里，新人入职后看不懂、接不上，交付与协作高度依赖口口相传。[来源：company_doc_init.rst §1.1]

本项目的目的是把"人脑里的知识"变成"统一库 + 规范 + 流水线 + 可检索"的公司资产——建立集中文档库（单一信息源 Single Source of Truth）、统一模板与规范、Docs-as-Code 评审发布流水线，并完成存量迁移与新人 onboarding。[来源：company_doc_init.rst §1.1]

## 2. 目标与范围

### 2.1 项目目标（可验收）

| 编号 | 目标 | 验收标准 |
| --- | --- | --- |
| G1 | 建成统一文档库，替代散落存储 | 文档 100% 入 Git 版本库；站点可访问；权限分公开/内部/机密三级生效 |
| G2 | 统一六类文档模板与元数据规范 | 六类模板齐备；owner/version/status/评审记录 元数据必填且进 CI 门禁 |
| G3 | 建成 Docs-as-Code 流水线 | PR 评审 + CI 门禁（0 告警）+ 自动发布 + 可回滚；API 参考可自动生成 |
| G4 | 完成存量迁移与新人 onboarding | 关键存量文档入库；新人按路径 3-5 天可上手 |

[来源：company_doc_init.rst §1.2]

### 2.2 项目范围（高层级需求）

项目拆为 4 条高层级需求（Epic），编号 HL-01 ~ HL-04：

| 编号 | 需求 | 一句话说明 | 优先级 | 目标版本 |
| --- | --- | --- | --- | --- |
| HL-01 | 建立公司统一文档库 | 集中、可检索、带权限的单一信息源，替代 wiki/网盘/个人电脑 | P0 | R1（2026-Q4，示意） |
| HL-02 | 统一文档规范与模板体系 | 六类文档（需求/设计/API/手册/安装/发布 FAQ）模板与元数据规范 | P0 | R1（2026-Q4，示意） |
| HL-03 | 建立 Docs-as-Code 评审与发布流水线 | 入版本库 + PR 评审 + CI + 静态站发布，变更可追溯、发布可回滚 | P1 | R2（2027-Q1，示意） |
| HL-04 | 存量文档迁移与新人 onboarding | 存量关键文档按模板迁移入库，产出 3-5 天 onboarding 路径 | P1 | R3（2027-Q2，示意） |

[来源：company_doc_init.rst §1.3]

**范围边界**：本期方案以"文档含公司内部信息、需分级权限"为主场景；起步阶段先用 Sphinx 自带静态站，检索门户（Next.js）可后置。[来源：company_doc_init.rst §2.1.1]

## 4. 里程碑计划

按"四步搭建法"推进，各步以可验收交付物为节点：

| 步骤 | 要干什么 | 验收要求 | 交付物 |
| --- | --- | --- | --- |
| 一 · 打地基 | 建仓库、定目录与命名规范、起 Sphinx 骨架、定主题与版心 | 构建 0 告警出站、目录 lint 通过 | 可访问的空站点 |
| 二 · 通链路 | 打通 Doxygen → Breathe → Sphinx 抽取链，先做一个模块的 API 页 | 解压 objects.inv 后该模块 C/C++ 域符号覆盖 100% 公开符号 | 首批 API 参考页 |
| 三 · 建流水线 | PR 评审 + CI 门禁 + 自动发布 + 多版本并列 + 回滚演练 | 回滚演练成功一次；门禁能拦下死链与元数据缺失 | 流水线 v1.0 |
| 四 · 产内容与交接 | 六类模板铺开、存量迁移、产出 onboarding 路径 | 六类模板齐备；新人按路径 3-5 天可上手 | 模板库、迁移清单、onboarding 路径 |

[来源：company_doc_init.rst §2.2.1.3]

**工期提示**：上面四步对应"完整启动计划（L3）"约 40-45 人日（按 1 名专职文档工程师计，理论下限）；中位预期约为 2 倍，兼职岗按 2-2.5 倍估算。此为示例估算，非排期承诺，待确认真实人力与并行度。[来源：company_doc_init.rst §2.2.1.3 / §2.1 开头重要说明]

## 5. 主要风险

| 风险 | 影响 | 应对（来源章节） |
| --- | --- | --- |
| 注释补齐是最大变量 | 研发部 Doxygen 注释覆盖率不足，API 自动生成目标（G3）落空 | 模板先行 + 统一注释规范 + 设覆盖率基线，由研发侧排期推动（§3.2.2.2） |
| pandoc 位置错，符号域被抹掉 | 函数签名降级为纯文本，跨文档符号引用失效 | 抽取链（Doxygen XML + Breathe）提供语义，pandoc 只做格式搬运（§3.2.3.1 / §3.2.4.1） |
| 敏感文档误入公开仓库 | 权限落在托管层，Sphinx 产物本身不分级 | 敏感文档不入公开库，入库前过权限检查清单（§3.2.1.1） |
| 该迁的没迁 / 迁了一堆垃圾 | 存量迁移价值打折，知识仍散落 | 全量盘点 + 留/改/弃三级判定，弃项留理由（§3.2.4.1） |
| 审批环节多、启动拖期 | 平台选型与预算审批阻塞 | 选型材料前置到季度规划会一次过会；预算与权限分级合并评审（§3.2.1.2） |
| 目录规范未先行，二次返工 | 各团队迁入后口径不一致需重做 | 目录 lint 脚本在 CI 强制校验（§3.2.1.1） |

[来源：company_doc_init.rst §3.2]

## 6. 需要决策的事项

1. **文档平台选型**：在 Sphinx（采纳）与 Docusaurus（备选，本期不采纳）之间确认。决定依据为"含内部信息 + 需 PDF/离线件 + C/C++ 接口自动生成 + 引用机器校验"四项硬差距；该结论由大模型评估生成、未经工程验证，建议作为决策起点而非终局。[来源：company_doc_init.rst §2.1]
2. **预算与专职人力**：是否配备专职文档岗直接决定工期（专职 L3 约 40-45 人日 vs 兼职 2-2.5 倍）。需 PMO 确认编制与预算。[来源：company_doc_init.rst §2.1.1 / §2.2.1.3]
3. **权限分级策略**：公开/内部/机密三级如何界定、机密档是否本期落地（建议先落公开/内部两档，机密档后置）。[来源：company_doc_init.rst §3.2.1.3]
4. **检索门户是否后置、何时启动**：起步阶段用 Sphinx 自带静态站，Next.js 门户（需前端开发）可后置，需确认启动时点与资源。[来源：company_doc_init.rst §2.1.1]
5. **存量迁移优先级与资源**：以盘点报告的留/改/弃清单与工作量估算，一次性确定迁移优先级与投入。[来源：company_doc_init.rst §3.2.4.9]

:::{note}
以上工时、工期、评分与选型结论均来自大模型评估（DeepSeek-V4.1-Flash），属**模型评估**且为**理论下限**，未做工程验证，请勿直接当作排期或承诺值。真实数值与起止时间待 PMO 与各团队确认。
:::
