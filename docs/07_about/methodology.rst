技术文档体系方法论（Docs-as-Code）
=======================================================

本文记录这套文档体系的设计取舍与落地链路：
**不是单篇文档怎么写，而是如何从 0 把团队的文档体系建起来、跑起来、持续运转。**

----

1. 为什么 Docs-as-Code
------------------------------------------

传统文档（Word / Wiki）的通病：版本混乱、评审靠人肉、改了不知道改了啥、新人看不懂。

Docs-as-Code 把文档当代码管：

- 文档源文件进 **Git** （版本、可追溯、可 diff）；
- 用 **Sphinx + reStructuredText** 写规范（本站点即该写法的实现）；
- 用 **CI（Jenkins / GitHub Actions）** 自动构建静态站；
- 改动走 **Pull Request + 评审** ，而非口头通知。

2. 全流程（实际跑通的链路）
-----------------------------------------------

::

   写文档 (.rst)
      │  git commit / push
      ▼
   提 Pull Request
      │  三方评审（见 §3）
      ▼
   CI 自动构建静态站
      │  修改前 / 修改后 双版本对比
      ▼
   评审通过 → merge → 静态站自动发布

3. 三方 PR 评审机制
---------------------------------------

每篇规范文档的 PR 至少三方评审：

- **领域技术主管** ：架构与技术方案正确性；
- **集成测试主管** ：可测性、测试覆盖是否可达标；
- **关联模块 Owner** ：跨模块接口契约一致性。

评审采用「 **修改前 / 修改后双版本渲染对比** 」—— reviewer 直接看改动点的前后差异，
而不是通读全文，评审效率与准确性大幅提升。

4. 新人 onboarding 提效（量化成果）
-------------------------------------------------------

用上述体系 + 标准化 HLD 模板，把模块级新人 onboarding 周期从数周压到 **3-5 天** ：

- 第 1 天：读模块 HLD（架构 + 线程模型 + 接口契约）建立全景；
- 第 2-3 天：读接口规范 + 跑通本地构建，动手改一篇小文档练评审流程；
- 第 4-5 天：在 reviewer 指导下提首个 PR，完成首个真实改动。

.. note::
   数字来自实际项目经验，项目背景已做泛化处理。

5. 发布门禁（Phase Gate）
---------------------------------------------

- 北向接口契约变更：必须走 Phase Gate 评审，提前一版本公告；
- 文档与代码同版本发布，避免「文档写着 v2、代码还是 v1」；
- 重大规范变更需附「影响面分析」与「回滚方案」。

6. 体系可落地范围
-------------------------------------------

1. 搭建 Sphinx + GitHub + CI 的文档基线（本站点即该基线的可实现形态）；
2. 定义 HLD / 接口规范 / 评审模板三件套；
3. 把「文档靠个人经验」转为新人 3-5 天可接手；
4. 以双版本对比评审替代通读全文式 review。
